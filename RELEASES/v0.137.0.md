# v0.137.0 — the server was not there when it was signed

An architecture correction, and the columns that were left empty by it.

**THE PHONE BUILDS THE RETAINED I-9.** The iOS app renders and seals the form on
the handset — where the nine SSN digits already are, and where the signatures are
drawn — and uploads the finished file through `attach_signed_i9`. The server does
not draw the retained page and does not receive the signatures separately.

v0.136.0 was written against the opposite assumption and half of it was wrong for
this reason. That half is reverted here; the half that was right is kept and
finished.

## Reverted: everything v0.136.0 did about the SSN

Removed, in full:

- `i9_pdf._ssn_lines` and its entry in Additional Information
- `include_full_ssn` on the mobile `generate_i9_pdf`
- `ssn` on the mobile `submit_i9_section_1`
- `site_policy` on the mobile `get_i9_form`
- the E-Verify entry in `_incomplete_boxes`, and `e_verify` on `_employer_block`
- `test_ios_contract.test_34`, **restored to the assertion v0.136.0 replaced** —
  that `include_full_ssn` is not an argument a handset has

The reasoning that produced it is not wrong, it is just no longer this app's
problem: the box is a nine-cell comb with `/MaxLen 9`, four digits in it read as
a number beginning `0000`, and a masked `XXX-XX-8888` truncates to `XXX-XX-88`.
All of that is now the phone's to deal with, on the page the phone draws. What
`render_i9_pdf` produces is the WORKING copy an operator prints from the Desk,
and a page that is not the retained record should not be commenting on a box the
retained record fills.

`_full_ssn`, `_store_full_ssn_enabled` and the `full_ssn` argument to `plan` /
`fill_i9_pdf` are **untouched** — they predate v0.136.0 by ninety releases and are
still how a Desk operator prints a comb deliberately.

## Kept: the metadata columns, and the Gulf of Guinea

Everything v0.136.0 did that was about storing facts rather than drawing pages
stands, because it is exactly what the new architecture needs more of:

- `section_1_signed_gps` / `section_2_signed_gps` on I-9 Form
- `list_a/b/c_doc_copy`, and `attach_onboarding_document` pointing them at each
  examined-document photograph as it is filed
- `pdf_seal._coordinates` no longer printing `0.000000, 0.000000` — an unset
  `Float` reading back as a point in the Gulf of Guinea, on the one page whose
  job is to state what was and was not observed
- `_fit`, which drops whole groups rather than slicing a sentence mid-clause and
  appending a full stop that made the fragment look finished

## New: the signed copy carries its own metadata

`attach_signed_i9` — and the mobile `upload_signed_i9` in front of it — now take:

    section_1_signed_at   section_1_gps_lat   section_1_gps_lon
    section_2_signed_at   section_2_gps_lat   section_2_gps_lon

**Because nothing else fills them any more.** Those columns used to be written as
a side effect of the server RECEIVING a signature. The retained page arrives
whole now, so on a phone-built form they stayed empty and the only timestamp on
the record was `signed_pdf_on` — which answers *when did the file arrive*, a
different question from the one 8 CFR 274a.2(h)(2) asks. A crew signs in an
orchard with no bars; the phone uploads at the shed an hour later.

**The timestamps are the client's claim, and are recorded as one.**
`submit_signature` refuses a client-supplied `signed_on` and stamps its own, on
the argument that a handset which could set it could backdate it. That argument
is sound wherever the server witnesses the event and does not survive the move —
stamping `now()` here would record the upload and label it the attestation, which
is a wrong answer rather than a missing one. So the claim is taken and **only a
FUTURE timestamp is refused**, that being the one claim that cannot be true and
the one a skewed or tampered clock produces. `signed_pdf_on` keeps the server's
own arrival time, unaltered and separate, so an audit can compare the two. The IP
is the server's own observation and is the only part of the packet the caller
cannot state.

**Nothing already recorded is overwritten.** A section signed at the pad was
timed by the server as the ink landed; an upload restating it keeps the better
record. The answer reports `signing_metadata` — the columns this call actually
filled — so a client cannot believe it wrote something it did not.

**Coordinates are named per section and read only what they name.** `as_gps`
grew explicit key pairs for this: a phone that got a lock for Section 1 and not
for Section 2 must not have an alias chain fall through to a bare `gps_lat` and
copy one section's location onto the other. Half a fix is still refused, and so
is the exact pair `(0, 0)`.

**Resolved before the file is touched**, so a bad timestamp refuses having
changed nothing — the same ordering `submit_i9_section_2` uses for its signer
check. A refusal that fired after the bytes were made private and re-pointed
would leave the file moved and the record not updated.

## Verification photos

Already handled and unchanged from v0.136.0: the app files each examined-document
photograph with `attach_onboarding_document`, which attaches the bytes to the
Employee and points the I-9's `list_a/b/c_doc_copy` at it as it lands. Nothing is
moved or re-uploaded, the link never raises, the Destroyed row is excluded by
name, and a retry converges rather than preserving a gap.

## KNOWN, NOT FIXED HERE: a phone-built I-9 can never reach `Complete`

Measured on the finished flow rather than predicted. After a full phone-built
run — both sections filed, the sealed PDF uploaded, metadata recorded:

    status                 = 'Awaiting Verification'
    signed_pdf             = '/private/files/signed-i9.pdf'
    section_1_signed_at    = <recorded>
    section_1_signed_gps   = <recorded>
    section_1_signature    = None
    unsigned_boxes()       = ["Section 1 (the employee's attestation)",
                              "Section 2 (the employer's attestation)"]
    advance_if_signed()    = ''      # no edge to move

`unsigned_boxes` tests the signature IMAGE columns, which nothing fills any more.
So every phone-built I-9 rests at `Awaiting Verification` permanently and the
compliance sweep raises `i9_section_1_unsigned` and `i9_section_2_unsigned` —
two Criticals — on forms that are signed, sealed and retained.

**Not fixed here on purpose.** It changes what `Complete` means on a federal
record and it touches four coupled things at once: `unsigned_boxes`,
`advance_if_signed`, the two compliance rules, and Section 2's own status gate.
Moving the status without moving the sweep would just relocate the disagreement.

The shape that looks right: treat the arrival of a signed copy WITH both
`section_N_signed_at` claims as satisfying the attestation test — the employer's
app asserting both signatures were made, with the retained page on the record to
show for it — and teach `unsigned_boxes` the same rule so the sweep and the
status cannot disagree. That is an operator's decision about a federal record and
it should be made deliberately.
