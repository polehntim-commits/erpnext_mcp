# v0.144.0 — the valve was right, the record about it was not

One tool. `update_irrigation_valve`. No new doctype, no new column, no change to
any existing signature.

---

## What was already true

`create_irrigation_valve` has been able to state a valve's rank, its parent and
its zone since v0.117.0, and it checks all three against each other at the moment
somebody states them: a Main filed underneath a Lateral is refused, a parent that
is not a valve is refused, and a zone that does not exist or belongs to another
entity is refused.

What there was no way to do was **correct any of it afterwards.**

`update_registered_asset` reaches the columns every asset has — description,
`nfc_uid`, `location`, the GPS pair — and it knows nothing about a valve. It
cannot set `valve_type` at all, and it will move a valve to a new `location`
without once asking what rank the valve on the other end of that link has. So the
only two ways to fix a miskeyed valve were to go through the Desk, or to retire
the tag and print a new one for a valve that had not moved.

## The refusal that only ran at insert was not a refusal

A check that runs at creation and nowhere else is a check anybody gets around by
creating the valve correctly and editing it a minute later. This release makes
the create's three refusals again, on the edit:

  * a parent that is not a valve, refused **by naming what it is** — the same
    answer `_valve_row` gives everywhere else, so a worker who pointed at a pump
    learns it is a pump;
  * a zone that is not on this site, or is somebody else's water;
  * a Main filed underneath a Lateral.

The last one is checked **from both ends**, because an edit can reach that line
two ways the create cannot. Moving a Main under a Lateral is the create's own
case. Re-ranking a Lateral *to* a Main while it still hangs off a Sub-Main is the
same upside-down line arrived at from the other side, and it is refused with the
parent named.

## And one refusal the create cannot make

A new valve has nothing underneath it. An existing one does — so the rank is
checked **downwards** too.

Demoting a Main to a Lateral while a Sub-Main still hangs off it produces exactly
the line the create exists to prevent, and `close_valve` would honour it: the
cascade walks `location`, and a line ranked upside-down is a line somebody shuts
from the wrong end. The children are consulted **only when `valve_type` is what
changed** — moving a valve to a different parent cannot alter what its own
children are, and a downward check on a reparent would refuse an edit *above* a
line that was already inconsistent *below*.

A retired child does not block a re-rank. It is not operated and the cascade
skips it.

## The loop

`location` is self-referential and nothing in the register refuses A → B → A.
Both `asset_tags._descendants` and `valves._ancestry` are written to survive one
— they carry `seen` sets and depth caps — which is the honest admission that the
data can contain one.

Filing a valve underneath its own descendant is the edit that **creates** one,
and this is the only place it can be caught. It is refused at any depth, using
the cascade's own walk, so the set of valves that would loop and the set this
refuses are the same set by construction.

## The tag ID is the one thing that does not move

The docname **is** the printable ID. It is on the label, it is what the QR
encodes, and it is the string every `Asset State Log` row carrying this valve's
runtime names. Renaming the record would leave the tag in the orchard pointing at
a valve that is no longer there, and would orphan the log rows the water report
is summed from.

So a rename is **refused rather than ignored**. `new_name`, `new_valve_id`,
`rename_to`, and a `valve_id` that disagrees with the `name` the valve was found
by, are all caught and named — a silently dropped key would report "2 field(s)
changed" over an edit that did not do the thing the caller asked for. The way out
is in the refusal: print the new tag, `create_irrigation_valve`, `retire_asset`
on the old one.

## Clearing is not omitting

An omitted argument leaves its column alone; that is what makes this safe to call
from a form that only sends what somebody touched.

`zone` and `valve_type` cannot be cleared **at all**. The first is the only link
this app has between a valve and a flow rate — without it `get_water_usage_report`
counts this valve's minutes and can price none of them, and names it in
`unpriced_valves`. The second is the rank, and an unranked valve is one
`create_irrigation_valve` will not file anything underneath.

A null `gps_latitude`/`gps_longitude` **does** clear the fix — and clears it to
empty rather than to `0`. `as_float(None)` is `0.0`, and `0.0, 0.0` is a real
coordinate in the Gulf of Guinea: a valve whose position was cleared must not
come back onto the map layer four thousand miles off the coast of West Africa.
`gps_lat`/`gps_lon` are accepted as spellings of the same two arguments, because
that is what the toggle and the scan call them and a handset should not have to
learn a third name for a latitude.

## An unranked parent blocks nothing here

A deliberate difference from `create_irrigation_valve`, and the one place this
tool is more permissive than the create.

`_rank` sorts an unknown rank **last**, and a valve registered through
`register_asset` has no `valve_type` at all — so the create's `parent_rank >
child_rank` test refuses to file anything underneath it. This tool is how such a
valve gets its rank in the first place, and it must not refuse a GPS fix or a
description over a rank nobody has stated yet. A parent that **has** a rank is
checked exactly as the create checks it.

## A retired valve is still editable

Unlike the toggle, which refuses one outright. Retirement says the valve is not
operated; it does not say the record about it was right. `retired` comes back on
the answer, so a screen that wants to warn can.

## What is not written

No `Asset State Log` row. Correcting a record is not operating the valve, and a
row here would put minutes into `get_water_usage_report` that no water accounts
for. The state, `last_state_change` and the scan stamps are untouched.

---

## GPS on the toggle — confirmed, not added

`toggle_irrigation_valve` has accepted `gps_lat`/`gps_lon` since v0.117.0 and
still does. Verified end to end for this release: the registry declares both
arguments, `valves.toggle_irrigation_valve` forwards them into
`log_asset_state_change`, and that writes `gps_latitude`/`gps_longitude` onto the
Asset State Log row — but **only on the row for the valve somebody was standing
at**. A cascaded close carries the time, the transition and its cause and makes
no claim that anybody was there, which is right: a fix taken at the turnout is
not where the lateral three hundred yards downhill is.

The mobile surface carries it too. `POST /farmops/api/mobile/scan_valve` takes
`gps_lat`/`gps_lon` and passes them to both halves — the scan stamp and, where
`toggle: true`, the state change.

Nothing was changed for this. It already worked.
