# v0.147.0 — the category an asset needs before it can exist

One tool. `create_asset_category`. No new doctype, no new column, no change to
any existing signature.

---

## What was already true

`create_asset` has refused an asset category the site does not have since
v0.7.0, and it is right to: an Asset Category is where ERPNext keeps the
fixed-asset, accumulated-depreciation and depreciation-expense accounts, per
company, and an asset filed under a category that has none has nowhere to
depreciate to.

What there was no way to do was **make one.** Every asset tool in this app
consumed categories and none of them created one, so the first step of standing
up a unified asset register — valves, tractors, wind machines, sheds, cabins,
each a category created once — was a trip to the Desk that the rest of the job
did not need.

## The signature that looks obvious does not work

`asset_category_name` and nothing else is the shape this looks like it should
have. It fails on every real site.

ERPNext marks the `accounts` table on Asset Category `reqd`. Frappe's own
mandatory check therefore refuses a category with an empty table — *"Data
missing in table: Accounts"* — before the controller runs, before any of
ERPNext's own account-type rules are reached. A category made from a name alone
is not a thin category; it is a document that cannot be saved.

The in-memory double this repository tests against does **not** model that
check. A name-only tool would have been green across the whole suite and broken
on the bench, which is the failure mode this app has been bitten by before. So
the refusal lives in the tool, one layer earlier, where it can name the argument
and list what the site actually has:

```
fixed_asset_account is required. ERPNext marks the accounts table on an Asset
Category as mandatory — a category with no accounts row is refused with "Data
missing in table: Accounts" — and the fixed asset account is the one column of
that row ERPNext has no company default to fall back on. Fixed Asset accounts on
Orchard Meadow, LLC: 1800 - Fixed Assets - OML. Nothing was created.
```

**One account, not three.** `accumulated_depreciation_account` and
`depreciation_expense_account` fall back to the Company's own defaults, which is
where ERPNext keeps them and where every category on a site otherwise repeats
them. `fixed_asset_account` has no company default in ERPNext, so it is the one
account this tool has to be given — and a site that has not set the Company
defaults either simply gets a row without them, rather than a crash on a column
its ERPNext does not have.

## The account types are checked before the insert, not during it

ERPNext's `AssetCategory.validate_account_types` throws on the wrong type at
save: *"Row #1: Account Type of 1110 - Bank Checking - OML should be Fixed
Asset"*. That is a true message about a row number in a table the caller never
saw, thrown by a controller three layers below the argument that was wrong.

The same rule, applied here, names the argument, says what type ERPNext demands
in that column, and lists the accounts of that type on the company. Nothing is
written either way — the difference is entirely in what the caller can do about
it.

## Asking for one that exists returns it

An Asset Category is `autoname: field:asset_category_name`. The name **is** the
docname, so there can only ever be one of each name, and "let there be a category
called Wind Machines" is already true when it is. Raising at a caller whose
desired end state already holds would make every seeding script wrap this tool in
an existence check it should not have to write.

So an existing name returns the category with `created: false` and the accounts
rows it found, and writes nothing. It does **not** add a row, fill in a missing
account, or touch a category it did not create: an Asset Category is a shared
master, and quietly editing one because somebody asked for a category by that
name is not what they asked for.

## The finance book row is ERPNext's schedule, not this app's

`depreciation_method`, `total_number_of_depreciations` and
`frequency_of_depreciation` go together into one Asset Finance Book row — all
three or none of them. ERPNext marks all three mandatory and its parent throws on
a total or a frequency below 1, so a row carrying one of the three is a row that
cannot be saved; refusing here says which of them is missing instead.

A zero is refused **for being zero**. `total_number_of_depreciations=0` is a
value somebody passed, not a value left out, and the presence check that decides
whether a finance book was asked for reads the raw argument rather than its
integer, so a 0 arrives at the "must be at least 1" refusal by name.

**Nothing in this app reads that row.** Assets created by `create_asset` carry
their schedule on the Asset Cost Profile and have ERPNext's own depreciation
switched off — the most important line in that feature. The finance book is
written because the category is a master an operator also uses from the Desk, and
a half-configured one is worse than none. A category created without one is
complete for this app's purposes, and the response says so rather than leaving
the reader to wonder.

## `company_name`, not `company`

ERPNext names the company column on Asset Category Account after its label:
`company_name`. This release is the first place in this app that **writes** one
of those rows, and it writes the column ERPNext reads, resolved through
`compat.first_field` so a site whose version spells it differently still gets a
row it can use.

## The refusal that sent people to the Desk now names the tool

`create_asset`'s unknown-category refusal has always listed what the site has.
It now ends "…so it has to exist first — **create_asset_category** makes one."
One sentence, and it is the difference between a dead end and a next step: a
refusal that lists categories and not the way to add one sends the reader to the
Desk for something the MCP can now do.

## What ships

| | |
|---|---|
| `create_asset_category` | One Asset Category, with the accounts row ERPNext will not save one without. **MUTATING**, off by default — `allow_create_asset_category`, under Assets and Depreciation. |

Sixteen tests in `tests_standalone/test_assets.py`, including the three that
matter most: that the missing-account refusal fires and leaves nothing behind,
that a wrong account type is refused before the insert, and that the category
this tool makes is one `create_asset` accepts.

Two entries in `tests_standalone/harness.py` are new because of it — the
`finance_books` child table, and `Asset Category` in `ERPNEXT_AUTONAME`, without
which the double serial-names a category "AC-00001" and the idempotence this
tool depends on cannot be tested at all.
