# v0.138.0 — the page it was signed on is the proof it was signed

The decision v0.137.0 wrote down and deliberately did not take. A phone-built
Form I-9 can reach `Complete` now, and the compliance sweep agrees that it should.

## What was wrong

Measured on the finished flow rather than predicted, and reproduced by
`RELEASES/v0.137.0.md` under "KNOWN, NOT FIXED HERE". After a full phone-built
run — both sections filed, the sealed PDF uploaded, metadata recorded:

    status                 = 'Awaiting Verification'
    signed_pdf             = '/private/files/signed-i9.pdf'
    section_1_signed_at    = <recorded>
    section_1_signature    = None
    unsigned_boxes()       = ["Section 1 (the employee's attestation)",
                              "Section 2 (the employer's attestation)"]
    advance_if_signed()    = ''      # no edge to move

`unsigned_boxes` tested the signature IMAGE columns and nothing else. Those hold
a picture of a signature captured at a pad THIS SERVER was holding, and since the
app began building and sealing the retained page on the handset the server is not
present at either signing — so nothing fills them, ever. Every phone-built I-9
therefore rested at `Awaiting Verification` permanently, and the sweep raised
`i9_section_1_unsigned` and `i9_section_2_unsigned` — two Criticals — on forms
that were signed, sealed and retained. An inspection board whose Criticals are
known to be wrong is a board nobody reads.

## The second witness, and it takes all three columns

    signed_pdf  AND  section_1_signed_at  AND  section_2_signed_at

That is the employer's own app asserting both attestations were made, with the
retained page on the record to show for it — which is what 8 CFR § 274a.2(b)(1)
asks an employer to have kept. It is a **weaker** witness than a capture this
server timed itself, and the app says so rather than hiding it: `signed_pdf_on`
keeps the server's own arrival clock, unaltered, beside the client's claim, and
an audit can compare the two.

**All three or none.** A signed copy on its own could be a blank form somebody
photographed. A pair of timestamps on their own is an app asserting a signature
with nothing behind it. Neither half is an attestation, and reading either as one
would move a federal record to `Complete` on less evidence than the record it
replaced.

**Per form, not per section.** The page the phone uploads is ONE page carrying
BOTH signatures; there is no such artefact as a signed copy of half an I-9. A
form part-signed at a pad and part-signed on a handset still answers correctly,
because the image columns are still read as well.

## Four things moved together, because they cannot disagree

1. **`i9.unsigned_boxes`** returns `[]` when `phone_attested` is true, and reads
   the image columns exactly as before otherwise. The first witness did not go
   away; it stopped being the only one.
2. **`i9.advance_if_signed`** did not learn a second rule. It asks
   `unsigned_boxes`, which now has two ways to answer — which is why the change
   went in there and not here. A status that could advance on evidence the sweep
   does not accept would be the same disagreement in the other direction.
3. **`i9_section_1_unsigned` and `i9_section_2_unsigned`** each gained one scope
   filter, built by `compliance_rules.i9_attestation_group()` — which reads the
   column names off `tools/i9` rather than restating them, so the sweep and the
   status cannot name different columns.
4. **Section 2's status gate** in `submit_i9_section_2` inherits it, so a Section
   2 filed AFTER the sealed page has landed completes the form in the one call
   instead of parking it.

`tests_standalone/test_i9_phone_attestation.py` checks the pair over all
**thirty-two** states of the five columns, read off the shipped rule specs: a
rule fires for a section exactly when `unsigned_boxes` names that section. The
matrix is measured for both answers, so it cannot pass by everything agreeing to
be quiet.

## The arrival is the moment, on this path

`advance_if_signed` was written for a signature landing at the pad, because that
was the only way one could land. **`attach_signed_i9` calls it now** — after the
columns are written, so it reads the metadata this call just recorded — and the
tool reports the status it LEFT BEHIND rather than the one it walked in on. A
handset told `Awaiting Verification` by the very call that completed the form is
reading the past. The mobile `upload_signed_i9` passes that through unchanged;
the response shape is the same, one value in it is now true.

It still moves one edge and only that edge. A scan filed against a form nobody
has verified moves nothing, and a form somebody set to Expired is not quietly
completed.

**And the third Critical goes with it.** `list_pending_i9_verifications` and
`i9_verification_overdue` both key on STATUS, so a form parked at `Awaiting
Verification` for ever was also an errand on somebody's dispatch list for ever
and a third Critical beside the two. Nothing had to be coded for that; moving the
status correctly clears it, and a test says so.

## `any` — one disjunction in the scope-filter vocabulary

Scope filters are ANDed, which is right and covers every shipped rule but this
one. "Not attested" is an AND of an OR and no arrangement of ANDed filters says
it. The alternative was moving two shipped rules out of the declarative
vocabulary and into Python, which is a bigger and more permanent widening.

    {"op": "any", "value": [ ...filters... ]}

It names no `field` of its own, passes when at least one member passes, and goes
**one level deep** — refused at authoring time otherwise, because a boolean
expression language belongs in `custom_python`, which a Compliance Rule already
has. An empty group is refused for the reason every other check in
`parse_filters` exists: it passes every row, so the rule would look scoped and be
unscoped. A group whose columns this site has not got **passes**, the same
fail-safe direction every absent column takes here, and says so in a warning.

`compliance_rules.filter_fields` is the small consequence: the two callers that
build a SELECT from a filter list can no longer read `field` off each entry.

## The patch, because the seeder will not do it

`seed_compliance_rules` checks the `rule_id` and leaves anything it finds alone —
deliberately, so an operator's edit is not corrected back on every upgrade. Every
site installed before this release already has both rule rows with the old scope,
so `erpnext_mcp.patches.widen_i9_attestation_filters` appends the group to the
live row on migrate. It **appends** rather than replaces, so a filter an operator
added to narrow the rule for their own operation survives; it is idempotent on
the columns the group reads, so a second `bench migrate` does not add a second
group; and it never raises. Existing alerts on attested forms are dismissed by
the next sweep, which stops observing them.

It edits the live row rather than superseding it, which is the opposite of what
`update_compliance_rule` does. Superseding exists so an alert raised last April
can be read against the definition that raised it. The alerts this suppresses
were **wrong when they were raised** — they assert that a signed, sealed,
retained federal form is unsigned — and preserving a definition so those can be
faithfully re-derived preserves nothing anybody wants.

## Also fixed: two audit rows that have never been written

Found by the test asserting the completion reaches the log, not by looking.

`I-9 Audit Log.action` is a Select and it did not carry `Completed` or
`Signature Collected`. `_log_action` swallows an insert it cannot make —
deliberately, because an audit row must never be the reason a signature is lost —
so since v0.64.2 **every** `advance_if_signed` completion and **every**
`collect_form_signature` capture on an I-9 has been silently dropped. The two
transitions an inspection is most likely to ask about were the two with no row
for them. Both options are on the DocType now; neither call site changed.

## Not touched

`i9_supplement_b_unsigned` is deliberately absent from all of this. A
reverification is signed in a child row, and a sealed Section 1/2 page says
nothing about it.

`section_1_signature` and `section_2_signature` are unchanged, still written by
`collect_form_signature`, and still the better evidence where they exist. Nothing
about a genuinely unsigned I-9 changed: it rests at `Awaiting Verification` and
raises exactly what it raised before.
