# v0.142.0 — the Pearl blocks link to their own catalogue

Multi-variety support for `Field`, requested directly: "the Pearl blocks have
multiple varieties (Black Pearl, Burgundy Pearl, Ebony Pearl) planted in one
field. We need a child table." — revised mid-build on a second look: "variety is
already nested under crop as well. So we just need to link the Field and the
crop variety together somehow to make a list of varieties... Don't duplicate the
catalogue fields."

---

## What was already true

`Field.variety` and `Field.rootstock` are flat `Data` columns — one variety, one
rootstock, per block. Every real orchard has blocks that respect that and blocks
that do not: the Pearl blocks carry three named cultivars in one field, and a
single column can hold exactly one of them.

Separately, `Crop.varieties` already holds a catalogue — `Crop Variety`, one row
per cultivar per crop, with grafting, pollination group, expected yield, years to
maturity and target Brix. The first pass at this feature missed that and built a
second, parallel set of columns on a new `Field Variety` table — `acreage`,
`row_count`, `rootstock`, `planting_density_per_acre` alongside `variety` — which
would have made `Field Variety.rootstock` a second, driftable answer to a
question `Crop Variety.rootstock` already exists to answer. Caught before it
shipped, and the design below is the corrected one.

## What this release adds

**`Field Variety`, a new child table, is a LINK to the crop's catalogue, not a
copy of it.** Three columns: `variety` (the cultivar, spelled as the crop's own
catalogue spells it), `percentage` (share of the block this variety covers,
0–100, optional), `planting_year` (when THIS variety went in, where it differs
from the block's own). Grafting, pollination group, yield and Brix are not here
— they stay on `Crop Variety`, read through the block's `crop`.

**`variety` cannot be a Link field**, because `Crop Variety` is itself a child
table (`istable: 1`) and a Frappe Link field resolves against a standalone
DocType's own table, not a row nested inside another document. So it is free
text — checked on save, not merely hoped to agree.

**`Field._check_varieties` is the checking**, on the same shape
`Crop._resolve_variety` already uses for `Crop Variety Water Requirement` and
`Crop Variety Protocol` reaching back into `Crop.varieties`:

- `crop` on a `Field` is free text, not a Link — most blocks are registered
  before anybody has built the crop catalogue. So the catalogue check applies
  ONLY when a `Crop` record named `self.crop` exists AND lists at least one
  variety of its own. A block whose crop was never turned into a catalogue
  record keeps whatever spelling was typed, the same way `Field.crop` itself
  does.
- Where the catalogue does exist, every `varieties` row must name one of its
  entries (case-insensitive), and the row is rewritten to the catalogue's own
  spelling on a match — so a later reader joining the two is a plain equality
  rather than a second casefold. A row naming anything else is refused, with the
  catalogue's actual list named in the refusal.
- The `percentage` values across the table cannot sum past 100 — the same
  "cannot both be true" arithmetic `_check_parcel_acreage` already applies to a
  parcel's blocks, applied here to one block's own varieties. Less than 100 is
  the normal case: an unrecorded remainder, or simply not every row filled in.

**`create_field` and `update_field` take a `varieties` argument.** The tool
layer (`farm._field_variety_rows`) validates SHAPE ONLY — unknown keys refused,
`variety` required, `percentage`/`planting_year` coerced — and leaves the
catalogue-membership and percentage-sum checks to the controller, the same split
`agronomy._water_rows` already leaves to `Crop._check_water_requirements` rather
than duplicating. `update_field` replaces the table wholesale rather than
merging, on `agronomy.update_crop`'s own reasoning: these rows carry no stable
key a caller can see, so there is no principled way to tell "the same row,
updated" from "a different row that happens to share a name."

**Every reader that describes a Field now reports `varieties` beside the legacy
columns** — `_describe_field` gained a fourth, batched parameter on the same
shape `counties` and `observed` already use, so a list of fifty blocks costs one
extra query rather than fifty. All seven call sites were updated: `list_fields`,
`get_field`, `create_field`, `update_field`, `get_parcel_field_summary`,
`find_fields_containing_point`, `find_fields_by_h3_cell`.

**`by_variety` now counts a multi-variety block once under every cultivar it
grows,** falling back to the legacy `variety` column only for a block with no
child rows. **`known_varieties`** unions both places a variety can be recorded,
so a suggestion list built from only one cannot silently drop the other.

**The mobile `create_field` route accepts `varieties` too**, as a native JSON
array or a JSON-encoded string — `_field_varieties_arg` gives it the same
tolerance `_receipt_items` already gives `create_scale_ticket`'s `items`.

## The migration

`backfill_field_varieties` copies each block's existing single `variety` into
its own Field Variety row **at 100%** — the whole block being that one variety is
exactly what a single column claiming to speak for the whole thing already
meant. The copied row still has to pass `_check_varieties`: where the block's
crop resolves to a real catalogue, the spelling is checked and corrected the same
as a caller's own `varieties` argument would be. A block whose crop's catalogue
exists but does not list the spelling `Field.variety` already holds is counted in
`not_in_catalogue` and reported by name rather than silently skipped — that block
needs a person's correction, not a guess this patch has no business making.

It is a seed and not a sync, and it only ever fills a block with no Field Variety
row of its own. `Field.variety` itself is never touched. It does not raise: a
`bench migrate` exception here would abort the migration for the entire bench,
and a block left with no Field Variety row is exactly the block every site had
this morning.

One real cost, named rather than hidden: appending a child row needs
`doc.save()`, and `doc.save()` always stamps the parent's `modified` timestamp —
there is no `update_modified=False` escape hatch for a child-table write the way
there is for a plain column. Every migrated block's `modified` date moves to the
day this patch ran.

## Tests

`tests_standalone/test_farm.py` — `CreateFieldVarieties` and
`UpdateFieldVarieties`: the shape of a `varieties` row round-trips; an unknown
key or a missing `variety` is refused with nothing written; the catalogue's own
spelling is written back when a matching `Crop` exists; a variety not in that
catalogue is refused and names what the catalogue does have; a block whose crop
has no catalogue at all is not checked; percentages summing past 100 are refused,
summing to exactly 100 are not; `update_field`'s `varieties` replaces the table
wholesale, is a no-op on the rest of the block when omitted, and an empty list
clears it.

`tests_standalone/test_patches.py` — `BackfillFieldVarieties`, nine tests: the
missing-DocType survival case, the empty-site skip, a successful 100%-share copy
verified by re-reading the child table, the catalogue-spelling correction, the
`not_in_catalogue` report path, idempotence on a second run, that an
already-linked block is left alone, and that a block with no variety at all is
not even scanned.

`tests_standalone/harness.py` — `Field Variety` registered in `APP_DOCTYPES` and
in `CHILD_TABLE_SOURCES` as `(("Field", "varieties"),)`, on the same entry `Crop
Variety` has for `Crop`. A third, unrelated bug surfaced while writing these
tests and was fixed alongside them: `varieties` was missing from
`REHYDRATED_CHILD_FIELDS`, so a child row loaded by `frappe.get_doc` — rather
than freshly `doc.append`ed in the same call — stayed a plain dict, and
`Field._check_varieties`' `row.variety = found` (the same idiom
`Crop._resolve_variety` already uses) raised `AttributeError` instead of
behaving like a document. Real Frappe always wraps loaded child rows regardless,
so this was standalone-double-only — but it would have hidden a genuine
`ValidationError` behind a crash on the harness's own `update_field` tests, which
is the failure mode `test_patches.py`'s own module docstring exists to catch.
