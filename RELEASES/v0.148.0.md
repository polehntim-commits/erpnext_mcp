# v0.148.0 — the tag on the machine and the asset on the books

Phase 3 of the unified asset register. No new tool, no new route, no change to
any argument iOS already sends. Three columns on ERPNext's `Asset`, one
checkbox, and one new module that connects two registers which have been
describing the same machines to each other in silence.

---

## The problem, stated as it actually is

A worker registers a tractor from the handset. It lands in `Asset Register` —
this app's own doctype, where the printed tag, the QR, the NFC UID, the scan
history, the service schedule and the hour meter live, and where Farm Task,
Compliance Alert, Accident Report, Crop Observation, Spray Application, Spray REI
and Asset State Log all point through a Link field.

It does not land in ERPNext's `Asset`, which is where the fixed-asset register,
`export_insurance_schedule`, the depreciation run and Sustainable CF/Acre all
look.

So the machine exists twice on one site and neither copy knows about the other.
An asset registered in the field is invisible on the books; an asset bought
through the books has no tag. On the deployed site that reads: thirty-three
irrigation valves in `Asset Register` and one record in `Asset`.

## Why this is a mirror and not a migration

The brief this was built from asked for the store to move — for the sidecar to
CRUD ERPNext's `Asset` instead of its own register. It cannot, and the reasons
are worth writing down because they will come up again.

**ERPNext's `Asset` refuses what a field registration has.** It is a submittable
financial document. The doctype marks `item_code`, `company`, `location` and
`purchase_date` required; `validate_asset_values` throws
`MandatoryError("Gross Purchase Amount is mandatory")` on a zero;
`validate_item` refuses any Item that is not a non-stock fixed asset; and
`validate_cost_center` throws unless the asset or the company names one. A valve
somebody tagged while walking a line has none of those. All thirty-three on the
deployed site read `purchase_value` 0.0 with no acquisition date.

**The docname is the sticker.** `Asset Register` is `autoname: prompt`, so
`40-N-1` in the database is `40-N-1` on the zip-tied tag in the orchard.
ERPNext's Asset is a naming series. Moving the store renames every asset and
reprints every tag.

**Eight doctypes link to it.** Moving the store repoints all of them.

So the register keeps the ground truth and this release writes a **second**
record beside it — an ordinary ERPNext Asset, in draft, carrying a Link back to
the tag — so the same machine appears where an accountant, an adjuster and a
lender look for it.

## Most tags do not mirror, and that is the correct behaviour

The tempting way to get all thirty-three valves onto the books is to invent what
ERPNext demands: a nominal dollar, or today's date, or ERPNext's
`is_composite_asset` flag, which skips the gross-amount check because a
capitalization entry is supposed to supply the value later.

Each one puts a number nobody measured into the fixed-asset register — and that
register is what the depreciation run, the insurance schedule and Sustainable
CF/Acre are computed from. A fabricated cost basis does not stay in the row it
was invented in.

So the gate is: **a tag mirrors when it carries a purchase value and an
acquisition date.** Otherwise it does not, and the reason comes back naming both
missing arguments at once:

```
the tag was registered, and it is not on the books yet because purchase_value and
acquired_on are not set. ERPNext's Asset is a financial document: it marks
purchase_date required and throws "Gross Purchase Amount is mandatory" on a zero,
so an asset mirrored without them would carry a cost basis nobody measured into
the depreciation run, the insurance schedule and Sustainable CF/Acre. Supply them
with update_registered_asset and the Asset is created then.
```

A tractor registered from the handset with its price is on the books the moment
it is registered — `register_asset` has taken `purchase_value` and `acquired_on`
since v0.78.0. A valve tagged with neither stays a tag until somebody says what
it cost, and `update_registered_asset` is where that happens.

**A `purchase_value` of exactly 0.0 is not a purchase value.** It is what every
valve on the deployed site carries and it is what ERPNext itself throws on, so it
refuses like an absent one. There is a test named after it.

## What gets written

| On the Asset | From |
| --- | --- |
| `asset_name` | the tag, then the description — `40-N-1 — 40 acer End of Main Line` |
| `item_code` | `FARM-ASSET-<TYPE>`, one fixed-asset Item per asset type, created once |
| `company` | the tag's company, never the session's |
| `location` | an ERPNext `Location` — the one named, else the site's only one |
| `purchase_date` | `acquired_on` |
| `gross_purchase_amount` | `purchase_value` |
| `is_existing_asset` | 1 — the farm already owns it; it is not being booked off an invoice |
| `calculate_depreciation` | **0** |
| `cost_center` | the company's default |
| `asset_register` | the tag. The Link that makes the two records one machine |
| `farm_asset_type` | Tractor, Wind Machine, Irrigation Valve … |
| `asset_register_synced_at` | when the mirror last agreed with the tag |

**`calculate_depreciation = 0` is the single most important line**, for the same
reason it is in `create_asset`: ERPNext's daily scheduler posts depreciation for
every asset that has it set, and `run_depreciation_cycle` owns the schedule for
anything this app creates. Both posting means depreciating twice, silently,
monthly, in the background. There is a test that reads the flag off the stored
Asset.

**The Asset is a DRAFT.** Submitting one is somebody deciding the purchase is
real, which is not a thing a field registration decides.

## Money is written once

An edit to a tag's `purchase_value` refreshes **nothing** on an Asset that
already exists. `gross_purchase_amount` is a figure the ledger has been
reconciled against, and a field edit that restated it would move a balance from a
screen where nobody could see that is what they were doing. What a later edit
refreshes is identity — the name, the type, the photograph, the stamp.

This is the negative control most likely to rot: the obvious "keep the mirror in
sync" refactor copies the value across on every edit, and every other test in the
module still passes when it does. That one has a test of its own, and the test
was checked by making the change and watching it fail.

## Retiring a tag does not dispose of the asset

ERPNext disposes of a fixed asset through a scrap or sale journal that posts to
the general ledger. `retire_asset` writes a date on a register row. They are not
the same act, and this release will not turn one into the other. What
`retire_asset` does now is *report* the Asset and say so:

```
the tag is retired. ERPNext Asset ACC-ASS-2026-00034 is UNCHANGED and still on
the books — disposing of a fixed asset posts a scrap or sale journal to the
general ledger, which is a decision made in the Desk and not a consequence of
retiring a tag.
```

## The photograph belongs to one record and shows on both

A Frappe `File` belongs to exactly one document, and `_attach_photo` gives it to
the Asset Register — which is where `export_insurance_schedule` reads
attachments from, so taking it away would empty an insurance schedule to fill a
thumbnail. `Asset.image` is an Attach Image, which stores a URL and does not need
to own the file. So the photograph shows on both records and belongs to one.

## Three columns and not twenty-three

`Asset Register` carries GPS, a serial number, a model, a service schedule, an
hour meter and two scan stamps, and the obvious build of this feature copies all
of them onto Asset so the Desk shows everything in one place. That is the shadow
layer `compliance_fields.py` argues against, aimed the other way: two editable
copies of one coordinate will disagree, and an insurance schedule reading one
while a dispatcher reads the other is worse than a single copy one click away.

Exactly one column here is not derivable from somewhere else — the Link — and
the other two exist to make it auditable: what kind of machine it is, so an Asset
list can be filtered without a join, and when the mirror last ran, so drift is a
column rather than a discovery.

All three are **read-only**. They are written by `asset_mirror` and by nothing
else, and a denormalised copy a second person can type over is a copy that will
one day lie.

## It ships OFF

`mirror_assets_to_erpnext` on ERPNext MCP Settings defaults to 0, like every
other mutating capability in this app — and this is a stronger case than most,
because what it gates is this app inserting into a doctype ERPNext owns on a
trigger a worker with a handset pulls.

Turning it off is not a loss of data. `Asset Register` is the operational record
either way, and a site that leaves this off has a complete tag register and an
untouched book. The reply says which checkbox, because a silent no-op is
indistinguishable from a broken feature:

```
asset mirroring is off. Tick 'Mirror Field Assets into ERPNext Assets' on ERPNext
MCP Settings to have a registration also create the ERPNext Asset that puts this
machine on the books. The registration itself is unaffected either way.
```

## A failed mirror never undoes a registration

The same trade `_attach_photo` makes and for the same reason: the tag is the
record, the mirror is a second copy of it, and losing a tractor's registration
because its Asset could not be built would be the wrong way round.
`asset_mirror.sync` returns a verdict and raises nothing; anything unexpected
goes to the Error Log and the caller is told the registration stands. Every
refusal in the test module is asserted twice — the Asset was not written, **and**
the Asset Register row was.

## The mobile contract did not change

Not one argument iOS sends was added, removed or renamed, and no route moved.
What the replies gained is additive: `erpnext_asset`, `erpnext_asset_created`,
and `erpnext_asset_note` when there is something to say. A client that does not
know about them ignores them.

`erpnext_asset_note` is present only when there IS something to say. A key that
is always there and usually empty reads as "no problem" to somebody skimming,
and the interesting case is the tag that did *not* reach the books.

## Reads say how big the gap is

`list_assets` now reports `erpnext_asset` per row and `on_the_books_count` for
the page — in one query, not one per row, because it returns up to five hundred.
"How much of the tag register is on the books" is the question this feature
exists to make answerable, and counting a column by hand across five hundred rows
is not answering it.

`get_asset_detail` reports the Asset for the one tag it was asked about.

**A tag with two Assets reports neither.** Two Assets for one tag is two sets of
books for one machine; returning whichever came back first would make every later
sync update an arbitrary half of them and leave the other drifting in silence. A
write in that state refuses and says so rather than making a third.

## Also in this release

**`bulk_create_assets` takes `acquired_on`, `purchase_value` and
`replacement_value` per row**, and reports `mirrored_count`. Both new keys are
optional and both were absent before, so a caller sending the old shape gets
exactly what it always got. A row with a mistyped price is registered and simply
does not reach the books — a rollout of five hundred valves should not be lost to
one bad cell.

**`register_asset` and `update_registered_asset` declare the arguments they have
always read.** `serial_number`, `model`, `acquired_on`, `purchase_value` and
`replacement_value` were accepted by the handlers and absent from the registry
schemas, so a model calling these tools could not discover them. They are
declared now, along with the new `asset_location`.

**A stale test assertion on `hooks.doctype_js` is fixed.** It read
`len(files) == 2` — "one shared widget plus one per-doctype script" written as a
count — and Asset Register has had two scripts since v0.145.0, when
`irrigation_valve_map.js` joined `asset_register_map.js`. They are a legitimate
pair: each returns early on the other's records so they never both render. The
assertion had been failing on `main` since the day that landed. It now checks the
rule it was a proxy for — the widget is listed first and listed once.

## What a site does to turn this on

1. `bench --site <site> migrate` — `install_compliance_fields` adds the three
   columns to Asset.
2. Tick **Mirror Field Assets into ERPNext Assets** on ERPNext MCP Settings.
3. Optionally, `create_asset_category` (v0.147.0) for the types the farm has —
   Irrigation Valve, Tractor, Structure, Wind Machine, Housing Unit, Machinery &
   Equipment. A site without them still gets its Assets; `asset_category` is
   optional on ERPNext's Asset and is only consulted when depreciation is
   calculated, which for a mirror it never is. Filing a valve under whichever
   category happened to exist would be worse than filing it under none, because
   a wrong category names the wrong depreciation account.

The thirty-three existing valves will not appear on the books until somebody
says what they cost. That is the feature working, not a gap in it.
