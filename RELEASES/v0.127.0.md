# v0.127.0 — the county's value wins

One behaviour change on one form, and it reverses a policy this app has argued
for at length since v0.34.0. An import from County GIS now **overwrites** what is
on the Parcel form. It does not skip a populated field, it does not ask, and it
does not report a disagreement instead of resolving it.

## What changed

| Form field | v0.34.0 – v0.126.0 | v0.127.0 |
|------------|--------------------|----------|
| `parcel_id` | filled if blank, else left and the difference reported | replaced |
| `acreage` | filled if blank, else left and the difference reported | replaced |
| `county` | filled if blank, else left and the difference reported | replaced |
| `boundary_geojson` and everything derived | replaced | replaced, unchanged |
| `title_holder` | never written | never written |

## Why the old policy was defensible, and why it goes anyway

The comment it is replacing said this, and every word of it is a real argument:

> AN EMPTY FIELD BEING FILLED IS NOT AN OVERWRITE, and that line is the whole
> policy here. A parcel whose acreage was typed off the deed and a county whose
> GIS says something different are two sources that disagree, and the app's job
> is to say so rather than to pick.

Two sources that disagree is the right description. Declining to pick between
them is what turns out to be wrong here, because **they are not two independent
sources.** The assessor, the deed and the tax bill all describe the lot the
county's layer describes — that is the whole reason this integration is worth
having. A figure sitting in `acreage` is a transcription of that same lot, made
at some point by a person reading one of those documents. When a transcription
and its original disagree, the original is not a competing claim; it is the
thing the transcription is of.

So the app was reporting a difference and leaving the operator to resolve it by
hand, every time, for a question that has the same answer every time. **This is
an operator's decision rather than a deduction**, and it has been made.

## What is reported

Everything that moved, in the summary after the save, with the old value beside
the new one:

> - Assessor Parcel ID: 2N11E35BA-01600 replaced with 1N 13E 7 200, from the county.
> - Acreage: 41.5 replaced with 131.43, from the county.
> - County: Sherman replaced with Wasco, from the county.

**A report, not a confirmation.** Nothing waits on it and nothing is skipped
pending an answer. It exists because after the save the summary is the only place
the previous value still exists, and that is what makes a wrong import
recoverable by hand.

A field the county said nothing about is **not touched**. Blanking a populated
field because the layer happened to be silent about it would be destroying data
rather than importing any, so the only reason a field is skipped is that there is
no value to write. A value that already matches is written past in silence.

**A `Float` field at zero reads as blank, not as a discarded figure.** `acreage`
on a Parcel nobody has typed one into is `0` — not `null`, not `""` — so a blank
test that knew only those two would tell somebody creating a parcel that
"Acreage: 0 replaced with 131.43". The zero rule is restricted to values that are
really numbers, because a Data field holding the string `"0"` is a value somebody
typed. It decides the wording only; both branches write.

## The one real cost, stated plainly

**The acreage guard can no longer fire on an import.**

`set_parcel_boundary` refuses a polygon whose enclosed area disagrees with the
recorded acreage by more than a quarter, and until now that refusal was the app's
automatic answer to "the wrong tax lot was imported" — a parcel recorded at 131
acres would not accept a 41-acre lot's shape, and the operator found out because
the save failed.

Overwriting the acreage with the county's own figure first means the polygon is
then compared against a number that came off the same measurement. They agree by
construction. The guard is still there and still runs; it just cannot catch a
mis-typed tax lot any more, because the wrong lot now arrives with its own
matching acreage.

**What replaces it is the preview, which was always the better check and is why
it exists.** The county's shape is drawn dashed on the satellite image next to
the block the operator already knows, and nothing is written until they press
Apply on that row. A wrong lot is obvious there in under a second, in a way an
acreage percentage never was — and the account-number search added in v0.126.0
makes the wrong lot much less likely to be fetched in the first place.

**The guard still protects every other caller.** It lives in
`set_parcel_boundary`, which none of this touches: the AI, the phone and a
hand-drawn polygon all still meet it with whatever acreage the record holds.

## `title_holder` is still never written, and that is not an exception

It is a Link to a Related Party on this site; the county's `Taxpayer` is free
text off a tax roll. Writing one into the other is not "use the county's value" —
it is inventing a link between two registers by string match, which is how a
parcel ends up owned by the wrong entity in an accounting system. The name is
reported so a person can set it themselves.

## The tests

`test_gis_import.py` goes from 73 to 79. `TheCountyValueWins` is new, and reads
the JavaScript structurally rather than asserting substrings of it — the claim
worth pinning is that **no branch can skip the write**, and a file that merely
contains the words `set_value` proves nothing about whether a condition guards
it. So the test asserts that `frm.set_value` appears *before* every test of the
existing value inside `consider`, that there are exactly two early returns and
that neither is about the field being occupied, and that the three overwritten
fields are exactly `parcel_id`, `acreage` and `county` — a fourth arriving has to
be a deliberate edit.

Four negative controls were run against it: restoring the v0.126.0 keep-branch
(3 failures), dropping the old value from the summary (1), quietly overwriting a
fourth field (1), and dropping the numeric-zero rule (1). The function was also
executed under a stubbed Frappe in node — 16 assertions covering overwrite, fill,
no-op, a silent county and `title_holder` — which is what caught the `Float`-at-
zero wording before it shipped.
