# v0.151.0 — the valves were never missing, the door was

One workspace, one patch, and one field the test double did not have.

---

## What this release does not do

It does not add an `Irrigation Valve` doctype.

It was asked to. The brief was that valves are "sidecar-only storage" invisible
to the Desk, and that a Frappe doctype should be created to mirror them the way
v0.149.0 mirrored assets onto ERPNext's `Asset`.

Every part of that premise is false on this site, and the check took one query:

```
query_doctype("Asset Register", filters={"asset_type": "Irrigation Valve"})
→ count: 33
```

All thirty-three valves are already Frappe documents. They are `Asset Register`
rows whose `asset_type` is `Irrigation Valve`, they have been since v0.25.0, and
they render in the Desk today at

    /app/asset-register?asset_type=Irrigation%20Valve

Every field the brief listed as sidecar-only is an existing column:

| asked for | already is |
| --- | --- |
| `valve_id` | the docname — `autoname: prompt`, so the docname IS the tag string |
| `valve_type` | `valve_type`, in a section that shows only for valves |
| `current_state` | `current_state` + `last_state_change` |
| `company` / `zone` / `parent_valve` | `company` / `irrigation_zone` / `location` |
| `qr_code` / `nfc_uid` | `qr_url` / `nfc_uid` |
| `installed_date` / `description` / `retired` | `installed_date` / `description` / `retired_at` |
| `gps_latitude` / `gps_longitude` | real Float columns, on every one of the 33 |

There is also already a valve-only Desk map: `irrigation_valve_map.js`, shipped
v0.145.0, which draws a DRAGGABLE pin and is wired in `hooks.py`.

"Sidecar" does not apply either. In this repo the sidecar is the retired Flask
`farm_app`, whose contents `farm_app_migration.py` calls test data. Valves were
never in it.

`tools/valves.py` opens with the argument in full, under the heading **WHY THERE
IS NO `Irrigation Valve` DOCTYPE**: a second table of valves is a second account
of the same pipe — two rows for one gate, two states that disagree the first time
somebody corrects one, and two answers to "how long did zone 3 run" of which the
wrong one is whichever a water district happened to read. Building it would also
have stranded the QR payloads, the closing cascade, `get_irrigation_runtime`'s
arithmetic over `Asset State Log`, and v0.149.0's own mirror — which maps
`"Irrigation Valve"` to its Asset category by name.

So the register was left alone, and the three things actually wrong were fixed.

## 1. A door to the valves — `/app/irrigation`

This app shipped no workspace covering irrigation at all. Reaching the valves
meant knowing to search "Asset Register" in the awesomebar and then knowing to
set the Asset Type filter by hand. A register you have to already know about is
one an operator reports as missing — which is exactly what happened.

`irrigation_workspace.py` builds an **Irrigation** page with four cards. The
first is the release:

```python
{
    "label": "Irrigation Valves",
    "link_to": "Asset Register",
    "stats_filter": {"asset_type": "Irrigation Valve"},
}
```

`Workspace Shortcut.stats_filter` is read twice by Frappe's own widget — once for
the count badge, and once at `shortcut_widget.js`'s click handler, which sets
`frappe.route_options` from it before routing. One field, and the card both
**counts** the valves ("33 tagged") and **lands on a list already narrowed to
them**. That is the whole difference between a shortcut to the asset register and
a shortcut to the valves.

**There is deliberately no "Open Valves" card.** `current_state` is a JSON column
and a valve nobody has toggled is CLOSED with the column still EMPTY — see
`tools/valves.py::_state_of` — so a `stats_filter` of `{"current_state": "open"}`
would both miscount and mislead. `test_no_card_filters_on_the_state_column` is the
negative control that keeps it out.

### Built in code, not shipped as a `workspace/*.json`

The first draft of this was a JSON file in the module folder. That is the obvious
way and it is wrong here: a Workspace JSON is in Frappe's `IMPORTABLE_DOCTYPES`
and is **force-synced by every `bench migrate`**, so it would silently overwrite
an operator's rearrangement of their own landing page on every upgrade.

`dashboard._build_dispatch_workspace` argued this first and `onboard_worker`
follows it, so this does too: build it once, and never touch a page somebody has
arranged. `_workspace_is_empty` is that guard.

## 2. Every valve now has the rank its own line already stated

`valve_type` was blank on all thirty-three. That is not cosmetic.
`create_irrigation_valve` refuses a parent that outranks its child:

```python
parent_rank = _rank(str(parent_row.get("valve_type") or ""))
if parent_rank > _rank(valve_type):
```

`_rank` answers `len(VALVE_TYPES)` — 3, one past Lateral — for a type it does not
recognise, and an empty string is one. So a parent with a blank rank scores 3,
every real rank scores 0, 1 or 2, and **that guard refused every valve anybody
tried to hang off an existing one**, in a message naming the parent's rank as
`''`. `_rank`'s own docstring says unranked "blocks nothing"; that is true of a
blank CHILD and false of a blank PARENT. `update_irrigation_valve` already guards
both its comparisons with `if parent_type and`; `create_irrigation_valve` does
not.

`patches/backfill_valve_rank.py` fixes the data rather than the shipped refusal.
**It reads no names and infers nothing from them.** `Asset Register.location` IS
the hierarchy — the column the cascade walks and `_ancestry` climbs — and
`valve_type` is the rank ON that hierarchy, so the tree already states the answer:

- no valve above it → **Main**
- a valve above it and valves below it → **Sub-Main**
- a valve above it and nothing below → **Lateral**

"No valve above it" is `_ancestry`'s rule, not merely an empty `location`: a line
usually hangs off the block asset it waters, and `_ancestry` stops at the first
thing that is not a valve. Below the second level everything is a Lateral rather
than a fourth name this app does not have, which keeps the assignment monotonic
down every chain — so no valve this patch ranks can refuse a child the register
itself permits. `test_every_parent_it_ranks_can_still_take_its_own_children` is
that property.

It only ever fills a blank, never rewrites a stated rank, is idempotent, writes
with `update_modified=False`, and does not raise.

On OML it will rank `40-MAIN` and `40-MAIN-HI` as Main and the thirty-one valves
under `40-MAIN-HI` as Lateral.

## 3. The test double was missing the field this release turns on

`compat.has_field("Workspace Shortcut", "stats_filter")` answered **False** in
`harness.py`, because the double's column list had `color` but neither
`stats_filter` nor `format` — both of which real Frappe v15 has.

The guard around the filter therefore skipped it silently, and the page built,
and every structural test passed, and the valve card returned an **unfiltered**
register. The build was green and the feature was absent. Both columns are now on
the double.

## What is still not fixed, and cannot be from here

**No valve names an `irrigation_zone`, because the site has no Irrigation Zone
records at all** — `query_doctype("Irrigation Zone")` returns 0.

Two consequences:

1. `get_water_usage_report` can price no gallons. All 33 valves land in
   `unpriced_valves` and every water report comes back minutes-only.
2. `create_irrigation_valve` **requires** a zone and refuses without one, so it
   currently cannot register a valve on this site at all.

This needs zone records with real `flow_rate_gpm` figures, which is farm
knowledge and not a code change. A fabricated flow rate does not stay in the row
it was invented in — it becomes a number somebody files with a water district.
