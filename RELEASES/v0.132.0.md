# v0.132.0 — the refusal that could not see the value it named

Two one-line fixes, and two more that were found, written, tested and then
**reverted** because they were wrong. The reverts are the more useful half of this
release note.

## The idiom

    value = as_int(args, "key", DEFAULT) or DEFAULT

`as_int` and `_as_float` both already answer the default for a missing or empty
value. So the trailing `or` cannot fire on `None` and cannot fire on `""`. The
only thing it can ever catch is an **explicit zero** — which it then replaces with
the default, silently, and reports success.

It was found by a peer session whose `stale_after_hours: 0` became 16 and closed a
shift the refusal existed to protect. A regex grep for it here matched roughly
forty sites; a peer's fuller AST sweep, run while this release was being written,
puts it at **127 `BoolOp`-over-coercion sites, 78 of them harmless identity cases
and 49 that actually drop a zero**. Harmless means `as_int(args, "x") or 0`, which
maps `None → 0` and `0 → 0` — the same answer either way. The gap between forty
and 127 is the grep's fault, not the sweep's: a regex anchored on the helper name
misses every site whose coercion is spelled differently.

## What shipped

### `generate_mobile_login_qr` — a guard that named the value it could not refuse

```python
hours = as_int(args, "expiry_hours", DEFAULT_QR_HOURS) or DEFAULT_QR_HOURS
if hours <= 0 or hours > 168:
    raise ToolError("expiry_hours must be between 1 and 168 (a week). ...")
```

The `<= 0` half was written, correct, and **unreachable**. An explicit `0` became
`DEFAULT_QR_HOURS` on the line above, so the check never saw it. A caller asking
for a zero-hour credential was not told no — they were handed a **live, working
login QR on the default window**, with a success payload and a PNG.

That is the direction that matters. The mistake did not produce an error; it
produced a usable credential. The author's intent is sitting in the guard, and the
line above it silently defeated the half that mattered most.

### `list_expiring_work_authorizations` — a window nobody asked for

`days_ahead: 0` means "who is expired, or expiring today". It became 90, so a
compliance screen answered a question about today with three months of people. It
errs toward showing too much rather than too little — a superset hides nothing —
which is why it survived, but it is still not what was asked.

## What was reverted, and why it matters more

Two further sites were fixed, tested, and then put back. Both failed on the same
fact, and it is a sharper rule than the one this release started with:

> **An explicit zero is only a distinct value for an ARGUMENT.** A Frappe `Int`,
> `Float` or `Percent` field has no empty state — an unset one reads back as `0` —
> so for a stored column "explicitly zero" and "never set" are the same bytes, and
> no amount of fixing the coercion can tell them apart.

### `budget_engine.threshold_pct` — the `or` was accidentally load-bearing

The initial reading was that `threshold_pct = 0` is the strictest watch the field
offers — "tell me about any variance at all" — silently becoming the default 10%,
hiding alerts. That reading was wrong twice over.

Removing the `or` introduces a **`ZeroDivisionError`** on the next line,
`ratio = abs(pct) / threshold`. Proven by running it, not by reading it:

    RAISED: ZeroDivisionError division by zero

So the redundant-looking `or` was holding something up. And `threshold_pct` is a
`Percent` with a doctype default of `"10"` whose own description defines behaviour
only for positive values ("Warning at 1-2x this number, Critical past 2x" is
meaningless at zero). What a stored `0` **means** is undefined by the product.
Giving it a meaning — is any variance a breach? what is the ratio? what severity?
— is a product decision and a schema question, not a patch. Reverted; the code is
exactly as it was.

### `dispatch.actual_duration_minutes` — a fix the schema cannot carry

The comment directly above the line reads: *"A stated `actual_duration_minutes`
still wins: a foreman correcting a figure is making a claim about the past that
this app does not get to overrule."* The line then overruled exactly one stated
value — zero.

The write fix worked. The test still failed, `None != 0`, because the read path at
`dispatch.py:895` is `int(row.get(...) or 0) or None` — the same idiom on the way
out, deliberately mapping `0 → None` to mean "not recorded". And it is right to,
because `actual_duration_minutes` is an `Int` with no default: a stated zero and a
never-set field are **the same stored value**. The distinction the fix was trying
to preserve does not exist in the schema. Reverted.

## Why "never load-bearing" was the wrong rule

This release began with a tidy rule: *when the coercion helper already takes a
`default`, a trailing `or <that same default>` is redundant for null and harmful
for zero — never load-bearing.*

It is a good search heuristic and a bad fix rule. It failed on two of four sites
the same day it was written, and following it produces a `ZeroDivisionError` in
alerting code. The order that actually works is:

1. **Find** — a `BoolOp(Or)` whose left operand is a coercion call, whatever is on
   the right. Anchoring on "the same default" misses the value-corruption class
   entirely, where the fallback is `active_minutes(doc)` or `round(qty * rate, 2)`.
2. **Triage** — is the zero an **argument** or a **stored column**? A column
   cannot represent an explicit zero, so stop.
3. **Then** ask whether the fallback equals the default, and what the zero means.

## The tests

Five, and each of the two fixes has a matching negative control that was run:

| control | expected failure |
|---------|------------------|
| put the QR `or DEFAULT_QR_HOURS` back | `test_an_expiry_of_zero_is_refused_by_the_guard_that_names_it` |
| put the i9 `or 90` back | `test_days_ahead_zero_asks_about_today_and_not_about_ninety_days` |
| change `DEFAULT_QR_HOURS` to `1` | `test_an_absent_expiry_still_takes_the_default_window` |

The third exists because "remove the `or`" could otherwise be satisfied by
removing the default along with it, and nothing else in the suite would have
noticed — the control has to fail for the reason you meant, not one adjacent to
it.

Each fix also carries the other half: `days_ahead: 0` must still **find** somebody
expiring today, and a card minted with no `expiry_hours` must still take the
shipped window. A fix that made zero match nothing would pass the first assertion
of each pair alone.

## Not fixed here

`tools/dispatch.py:895`, `budget_engine.py` ×4, and the residue a peer session has
filed separately: `sales.py:641`, `mutate.py:304`, `blocklifecycle.py:313`,
`investment_report.py:604`.

**A correction, made before this release landed.** A draft of this note put
`sales.py:641` and `blocklifecycle.py:313` in the reverted column class. That was
wrong, and a peer session caught it. `_manual_lines` iterates the caller-supplied
`items[]` list, so `entry.get("amount")` is an **argument**; `blocklifecycle`
reads `args.get("acres")`. Both are the fixable class, and `sales.py:641` —
`amount = as_float(entry.get("amount"), ...) or round(qty * rate, 2)` — reprices
an invoice line explicitly set to `0` back to `qty × rate`, which is the worst
instance in the whole set.

**But they still need a different fix shape, and that is the part worth carrying.**
This note said above that "`as_int` and `_as_float` both already answer the default
for a missing or empty value". True for `as_int` (`args.py:116`, which takes a
`default`) and for the private `_as_float` in `budget_engine`. **Not true for
`args.as_float`:**

```python
def as_float(value, key: str) -> float:
    if value is None or value == "":
        return 0.0
```

No default parameter, and it never returns `None` — absent, empty and explicit
zero are indistinguishable *after* coercion, and `as_float(x, key, None)` is not a
valid call. So deleting the `or` at an `as_float` site silently changes the
**absent** case too: a missing `amount` would become `0.0` instead of `qty × rate`.
Those sites need a branch on the raw value *before* coercion:

```python
raw = entry.get("amount")
amount = as_float(raw, f"items[{index}].amount") if raw not in (None, "") else round(qty * rate, 2)
```

That is two fix shapes across the roughly forty sites, not one, and applying the
`as_int` recipe to an `as_float` site is a no-op or a regression that reads like a
fix.

**And a fixture trap for whoever takes `sales.py:641`:** the corruption needs a
non-zero rate. With `rate: 0` the fallback computes `round(qty * 0, 2)` = 0 — the
same answer — so a test written that way passes against the unfixed code and
proves nothing. The real case is `qty: 1000, rate: 0.62, amount: 0` → `620.0`.

The propagation problem is the real one. `tools/files.py:_resolve_max_bytes`
already gets this right and says so in a comment — "Not `as_int(...) or DEFAULT`:
that idiom turns an explicit 0 back into the default, so a caller asking for
something impossible gets a silent success instead of the refusal below" — and
roughly forty sites did not receive it. A comment has demonstrably failed as the
mechanism. An AST-scanning test with an allowlist for the harmless identity cases
is probably worth more than any single fix in this release.
