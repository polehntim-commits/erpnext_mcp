# v0.121.0 — the sidecar's data was test data, and two things in it were not

Farm App Retirement, Cycle 2 corrected. v0.120.0 shipped a ten-table
SQLite→ERPNext migration; the owner then said the sidecar's contents are TEST
data, and that only two things in it are real. This narrows the migration to
those two and builds the doctype the satellite half needed.

Two DocTypes, one migration narrowed from ten tables to four, one script, two
test modules, 76 tests.

---

## The correction, and why it was right

The migration was not wrong about how to move rows. It was wrong about whether
to move them, which is the more expensive kind of wrong: **migrating test data
into the system of record does not preserve anything, it contaminates a clean
register with rows nobody can tell apart from real ones afterwards.**

The evidence was sitting in the database the whole time and this release went and
looked at it:

```
  field                       6 rows   two of which are "Dry Block" twice
  field_satellite_metric      2 rows   both `moisture`, both 0.15, 15 seconds apart
  satellite_backfill_cursor   0 rows
  maximum_residue             0 rows
  mrl_research_session        0 rows
  country / commodity / market  0 rows each
  field.ndvi_path             NULL on all six blocks
```

Two rows fifteen seconds apart with the same value is somebody pressing a button
twice to see whether the fetch worked. That is what the whole sidecar database
looks like on this copy.

**WHAT THAT DOES AND DOES NOT PROVE.** This is the local development copy. The
production database lives in the Umbrel container and is not reachable from
here, so these counts are a fact about the copy that was in the tree and not a
measurement of production. The migration is therefore built to carry the real
data if production holds any, and to report honestly when it holds none.

## What still crosses

| SQLite table | → | why it is real |
|---|---|---|
| `maximum_residue` | MRL Record | Residue limits transcribed out of the EU, Codex, Japanese and US registers. Published regulation, transcribed by hand, weeks of attention to redo. |
| `mrl_research_session` | MRL Record | The research that produced some of those limits. |
| `field_satellite_metric` | **Satellite Metric** | The index series the imagery left behind — the small permanent thing an expensive download produces. |
| `satellite_backfill_cursor` | **Satellite Backfill Cursor** | How far back the archive has already been walked. |

`maximum_residue` is new here and is the more important half of the MRL ask:
v0.120.0 migrated only `mrl_research_session`, which is the transcript of asking
a question, and missed the table holding the answers the farm actually ships
fruit against.

Eight tables are gone: `field`, `iot_device`, `iot_reading`, `strategic_plan`,
`objective`, `market_participant`, `acquisition_target`, `competitive_move`.
**Their DocTypes remain** — the structure was the point of Cycle 1, and a farm
starting to log real devices needs somewhere to log them. What is not carried
across is the test rows that happened to be sitting in those tables.

## The satellite half, which is the part with money in it

"Preserve the satellite imagery so it doesn't need re-downloading" turns out to
be three different things, and only one of them is the imagery.

**The rasters themselves are not worth moving.** A Sentinel-2 tile is megabytes,
is re-downloadable from the provider's archive for years, and is useful for about
as long as it takes to compute a mean from it. On this copy there are none:
`Field.ndvi_path` is NULL on all six blocks. `raster_manifest()` reports what a
production copy still points at — path, size, and whether it is readable from
where the script is running — and **moves nothing**, because copying megabytes
across a container boundary is a `docker cp` an operator does with their own
hands, their own disk and their own timing.

**The numbers are worth keeping, and now have somewhere to go.** `Satellite
Metric` holds one index reading for one block at one moment. v0.120.0 folded only
the newest NDVI per block onto `Field.last_ndvi_*` and reported the rest of the
series as dropped, because there was no doctype to put it in. There is now, and
the whole series crosses.

**The cursor is the thing that actually answers the question.** `Satellite
Backfill Cursor` holds no measurement at all — just how far back and how far
forward imagery has been pulled for one block and one index. Without it a
backfill starts at the beginning and pays the provider again for twelve months
somebody has already bought. **Its cost of loss is invisible in the data and
visible on an invoice**, which is exactly why it is the sort of thing that gets
dropped in a migration.

Both doctypes refuse the failures that do not announce themselves:

- A reading outside its index's physical range is **refused, not clamped** — 87
  in a column that runs -1 to 1 is a decode with the wrong scale, and clamped it
  files as a very healthy block.
- SAVI keeps its own wider range (-1.5 to 1.5), so a legitimate SAVI reading is
  not rejected by NDVI's bounds.
- A pass dated after the server is refused; a satellite cannot have flown over
  yet, and the row would sort above every real reading for ever.
- A cursor whose `oldest_fetched` is after its `newest_fetched` is refused: a
  scheduler reading it fetches either nothing for ever or everything every night.

## The unit trap in the MRL data

`MRL Record.mrl_ppm` says ppm in its own name. `maximum_residue.mrl_unit` is free
text.

```
  mg/kg  →  ppm    same thing, converts silently
  ppb    →  ppm    × 0.001, converted and ANNOUNCED
  µg/kg  →  ppm    × 0.001, same
  anything else    REFUSED
```

300 ppb written straight into a ppm column is a limit **a thousand times too
loose** — the direction that clears a shipment it should have held. An
unrecognised unit is refused rather than assumed, and the refusal says so.

## The name join, and why it refuses

MRL rows reference a crop and a country by SQLite id. Nothing on this site's
`Crop` or `Market` carries those ids, so the join is on the **name** — the
weakest link in the whole exercise. It is therefore done once, exactly,
casefolded, with **no fuzzy matching of any kind**: every "cherries → Cherry"
rule is right four times and wrong once, and the once is a residue limit filed
against the wrong fruit.

A limit whose crop or market does not resolve is **refused**, not filed against
nothing. Both are `reqd=1` on `MRL Record`, so an earlier draft that warned and
migrated anyway would have turned a readable dry run into a mid-run insert
failure with part of the batch already landed. The report lists every unmatched
name; create or rename them and re-run, which is cheap because the migration is
idempotent.

refused for a doctype that is not on the site.

docker exec -w /home/frappe/frappe-bench <container> \
    python3 migrate_farm_app.py --database farm_app.db --site <site> \

`--tickers`, `--parcel` and `--rotate-tokens` are gone with the specs they
belonged to; a flag that outlives its spec is one somebody passes and watches do
nothing.

## What is not tested here

The two controllers' hooks are exercised by calling `validate` directly, because
**the standalone double does not run this app's controllers at all** —
`STUB_CONTROLLERS` covers ERPNext's own doctypes and nothing of ours. That is
real coverage of the logic and it is not evidence that Frappe invokes it; only a
bench run proves that, and `bench --site <site> run-tests --app erpnext_mcp` is
where it belongs.
