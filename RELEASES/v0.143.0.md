# v0.143.0 — the valves you cannot get a camera in front of

Four reads. No new tool, no new doctype, no new column.

---

## What was already true

`tools/valves.py` has carried `list_irrigation_valves`, `get_irrigation_valve`
and `get_valve_runtime` since v0.117.0, and `tools/farm.py` has carried
`get_irrigation_zone` since v0.9.0. All four were published on the MCP tool
registry alone.

What a **phone** could do at a valve was `scan_valve`, mounted in the same
v0.117.0 release. It answers the whole valve screen — state, the line above, what
is below, today's runtime, the one button worth drawing — and it needs a tag in
front of the camera to answer anything at all.

Probed on 2026-08-29 against the deployed sidecar, which answers
`{"ok": true, "service": "farmops-api", "version": "0.142.0"}` on
`/farmops/api/health` with no credential. A routed method answers **401** with no
credential; an unrouted one answers the sidecar's own **404**:

```
  POST /farmops/api/mobile/scan_valve              401
  POST /farmops/api/mobile/create_irrigation_zone  401
  POST /farmops/api/mobile/set_zone_boundary       401
  POST /farmops/api/mobile/list_irrigation_valves  404
  POST /farmops/api/mobile/get_irrigation_valve    404
  POST /farmops/api/mobile/get_valve_runtime       404
  POST /farmops/api/mobile/get_irrigation_zone     404
```

**`set_zone_boundary` was never missing.** It has been mounted since v0.110.0,
`MobileAPI.setZoneBoundary` names it, and the probe above gets 401 from it like
every other live route. A 404 reported against that path is one of two other
things: a **GET**, which this transport answers 405 to and says why — every
method here is POST, including the reads, because a GET carries its arguments in
a URL and a URL is logged by every proxy in between — or a deployment behind the
branch the report was written against.

## What the missing routes cost

**They were the irrigator's whole job.** Somebody walking a set opens a line of
laterals in order and comes back four hours later to shut them. The question
between those two acts is *which of these is still open*, and that is a list
rather than a scan. So is "what did this zone run last week" at the district
office, and so is opening a valve somebody scanned an hour ago from the seat of a
truck.

**A camera is the wrong instrument for exactly the valve that matters.** A tag
that has weathered, been painted over, or gone under a season's growth is the one
a worker most needs to read, and it is the one `scan_valve` cannot resolve. The
manual-entry box reaches the same route with a bare docname — but only for one
valve at a time, and only for a valve whose ID somebody already knows.

## The four routes

| Route | Delegates to | What the wrapper adds |
| --- | --- | --- |
| `list_irrigation_valves` | `valves.list_irrigation_valves` | a `field` filter, and `status` as the app's spelling of `state` |
| `get_irrigation_valve` | `valves.get_irrigation_valve` | `field` at the top level; four spellings of the tag ID as one argument |
| `get_valve_runtime` | `valves.get_valve_runtime` | the gate, and both date spellings declared |
| `get_irrigation_zone` | `farm.get_irrigation_zone` | the zone's valves and its total runtime |

**Nothing new is computed.** Every figure on these four answers comes out of a
tool the AI surface has been calling for releases, with its caps, its state
resolution and its refusals unchanged. The two things a phone asks for that those
tools do not take are built by calling *more* of the same tools, never by reading
the register a second way:

- **`field` on the valve list.** `Asset Register` links a valve to an
  `Irrigation Zone` and nothing links it to a block; `Irrigation Zone.field` is
  the only join this app has from planted ground to a pipe, and it is the same
  join `get_water_usage_report` walks for its own `field` argument. The block is
  resolved to its zones by `list_irrigation_zones` and the valve list is run
  against each. The merge is arithmetic over the tool's own rows — a per-zone
  total presented as a block's would be the same bug one screen further on — and
  `zones_measured` names the zones actually read, so a block past
  `valves.LIST_CAP` says which ones it stopped at instead of quietly shortening.
  A `zone` and a `field` that disagree are **refused**, not reconciled.
- **The zone's valves and runtime.** `list_irrigation_valves` for the list,
  `irrigation.get_water_usage_report` grouped by zone for the total — which is
  `get_irrigation_runtime`'s measurement rolled up, the same function behind
  `get_valve_runtime`'s `zone_rollup`, so the total on a zone screen and the
  total beside a valve cannot disagree. The report tool **raises** on an empty
  set and is right to: a water-rights figure measured over no valves is a lie in
  the shape of a zero. On a zone screen that is an ordinary state, so
  `total_runtime` comes back `null` with a note naming
  `Asset Register.irrigation_zone` and how to set it.

**`status` goes straight through unresolved** unless it is `all`. Anything the
state machine does not define is refused **by the tool**, listing every state it
does define — a wrapper that mapped an unknown word onto `closed` would answer a
question nobody asked, about a valve that might be winterized.

## The gates

**All four are open on enrolment**, which is this surface's rule for a read about
the caller's own work and the ground they are standing in. `routes.py` already
says of `scan_valve` that a valve "is what a worker in a block sees and a foreman
at a desk does not"; the irrigator walking the set is the least-privileged caller
here, and a dispatch gate would take their own work off their own handset.

**Nothing here writes.** `scan_valve`'s opt-in toggle remains the only way a
handset moves a valve, and it keeps its `WRITE_LIMIT`. The four reads are metered
at `READ_LIMIT` and none declares `mutating`.

**The company comes from the scope check and never from the body.** `company` on
the valve routes resolves through `_company`, so a valve of another entity reads
as though it were not there. The zone route is scoped by hand through
`_scoped_location`, for the trap `_set_one_boundary` documents at length:
`guard.require_scoped_doc` reads a column called `company` and all four location
registers call theirs `owning_entity`, so the generic check would have passed
everything.

## The iOS half

`MobileAPI.swift` names none of the four, so they are in
`test_api_mobile.PENDING_IOS_INTEGRATION` rather than in `MOBILE`, and
`test_ios_contract` is exempt — a Codable mirror written now would be an invented
contract rather than a copied one.

The client change is small on purpose. `get_irrigation_valve` answers the shape
`scanValve` **already decodes**: both come out of `valves._status`, which is why
that function exists. A handset that can render a scan renders this with a
constant and a call site, not a new model.

## Tests

`tests_standalone/test_irrigation_valves.py` gains
`TheHandsetReadsTheLine` — 27 tests driving the four routes over a fixture with
**two blocks and three zones**, because a `field` filter that fanned out over the
wrong zones, or over all of them, passes against a farm with one zone on one
block and fails in July.

Three of them are negative controls rather than assertions:

- a window that **excludes** the seeded run measures nothing, so a date argument
  that never reached the tool cannot pass the test above it;
- the cross-entity tests **enrol the outsider first**, because
  `harness.PermissionError_` subclasses `ValidationError` — a cross-entity test
  written without that line passes on the wrong refusal and goes on passing if
  the scoping is removed;
- `get_irrigation_valve` and `scan_valve` are asserted to agree key for key on
  the facts they share, because "the same shape" is a claim that quietly stops
  being true.
