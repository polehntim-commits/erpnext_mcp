# v0.123.0 — the registers a phone was standing in front of and could not reach

Seventy-two mobile routes. No new DocType, no new MCP tool, no existing tool
signature changed. The mobile route table goes from 202 to 274.

## What was actually missing

Every one of these seventy-two already existed as an MCP tool. The assistant
could call all of them; a handset could call none of them. That is a transport
gap rather than a capability gap, and it is worth naming because the registers
involved are the ones somebody is physically standing in front of — a CCP check
written at the line on the hour, the lot code on the bin in the picker's hands,
the sensor that stopped reporting from a block, the residue limit that decides
whether a load may ship.

## The premise that had to be corrected first

The brief for this work said the settings switches were the security gate and
route omission was not. **That is true of the MCP surface and false of this one.**
`settings.tool_enabled` reads `allow_<tool>` and is called by `mcp.py:108`. It is
never called by `api/guard.py`. Grepping `guard.py` for `allow_` returns only the
mobile kill switch, `farm_ops_mobile_enabled`.

So a route here is gated by `guard.endpoint` — kill switch, rate limit,
`FARM_OPS_ROLES`, live enrolment grant — plus whatever the wrapper body adds, and
by nothing else. Registering a route publishes it to every enrolled handset. The
gates below are therefore chosen per method rather than inherited from a settings
page, which is what the brief's own per-domain role table asked for anyway.

## The gates

| gate | count | what it covers |
| --- | --- | --- |
| open on enrolment | 34 | reads: plans, hazards, controls, monitoring, lots, traces, devices, limits |
| `guard.require_dispatch_role` | 26 | every write, plus `recall_drill` |
| `personnel.require_hr_role()` | 12 | the competitive registers, reads AND writes |

`recall_drill` is read-only and gated with the writes on purpose: it is a
management exercise against the lot register, not a read of one's own work.

The HR gate raises `ToolError`, not `frappe.PermissionError`, so it reaches the
phone as **400** where the dispatch gate reaches it as **403**. That is
pre-existing — every HR-gated method already on this surface behaves the same way
and the suite has always asserted the sentence rather than the code for them. It
is recorded here because `farmops_api/app.py`'s status table reads as though every
role refusal is a 403, and that is not true of this one.

## Scoping

Twenty-five methods scope on the docname through `guard.require_scoped_doc`,
which refuses another entity's document as NOT FOUND rather than as refused, so
its docnames cannot be mapped by watching which error comes back. Forty-two more
resolve a company through `guard.require_company` and let the tool filter on it.

**Five methods, across three registers, cannot be scoped, and each says so in its
own docstring.** Soil Compaction Profile has no `company` column; the IPM and
variety-care lookups are keyed on a crop rather than on a document. `require_scoped_doc` reads `company` off the row
and only refuses when it finds one, so on those it reads None, skips its check
and hands the docname straight back — the same failure v0.110.0 documented on
three other registers. They are site-wide
reference data, which is a property worth writing down rather than leaving to
look like an oversight.

## The test

`TheNewRegistersAreGated` in `tests_standalone/test_farmops_api.py` drives all
seventy-two over the real transport as a plain enrolled Field Worker and asserts
which of them refuse. A route table proves a method is REACHABLE; it says nothing
about who may use it.

It was checked against its own negative control rather than trusted for being
green: removing `guard.require_dispatch_role` from `create_monitoring_record`
turns it red with `400 != 403`, and removing `personnel.require_hr_role()` from
`get_market_participant` turns it red with the call falling through to
`market_participant is required`. Both return to green when the gates are put
back. A fourth test compares the three gate sets against the route table, so a
route added later and left out of this file fails here rather than going quietly
ungated.

## iOS

`MobileAPI.swift` names none of the seventy-two, so all seventy-two sit in
`PENDING_IOS_INTEGRATION`. The server half ships first and the iOS half is a
client change rather than a release of both, which is the order the boundary and
location routes landed in.

## Upgrading

Nothing is required. The routes are live on deploy; `/farmops` is mounted as one
prefix, so a route is published by having been added.
