# v0.152.0 — the register believed the worker, the attachment did not

One line of routing, and the reason it took a bench to find it.

---

## The complaint

Register a wind machine from the handset. The tag comes back. Then the
photograph of the machine comes back as this:

```
polehntim@gmail.com is not permitted to write Asset Register 40-5-MPH,
so nothing may be attached to it.
```

Not a bad file, not a bad tag, not a size limit. A permission — on the record
the same phone had just created, seconds earlier, on the same login.

It was not the wind machine. It was every asset: sheds, tractors, valves, pumps,
anything registered from a phone. And it was not only assets, which is the part
that took a permission table to see.

---

## What was actually wrong

Two routes on the same surface disagreed about who the caller was.

`register_asset` inserts with `ignore_permissions=True`. Every write route on
the mobile transport does — the transport's own gates are the access decision
there, and `docs/security.md` has said so since the surface existed. Three of
them run before a byte moves:

1. `guard.require_scope` — the caller is enrolled, and these are their entities.
2. `ATTACHABLE_DOCTYPES` — the doctype is one this app files evidence against.
3. `guard.require_scoped_doc` — the docname is a record *inside those entities*.

`attach_file_to_document` ran all three, and then `tools/files.py` asked Frappe a
fourth question: `frappe.has_permission("Asset Register", "write")`. On this
transport `frappe.session.user` is the person holding the phone, so that question
was answered by a DocPerm written for the Desk:

| register on `ATTACHABLE_DOCTYPES` | roles granted `write` |
| --- | --- |
| Asset Register | System Manager, Accounts Manager |
| Farm Task | System Manager, Accounts Manager |
| Farm Task Assignment | System Manager, Accounts Manager |
| Inspection Session | System Manager, Accounts Manager |
| Housing Inspection | System Manager, Accounts Manager |
| Compliance Alert | System Manager, Accounts Manager |
| Spray REI | System Manager, Accounts Manager |
| Document Validation | System Manager, Accounts Manager, Farm Manager |
| Accident Report | System Manager, HR Manager |
| Expense Receipt | + Farm Manager, Foreman |
| Scale Ticket | + Farm Manager, Foreman |

Nine of the eleven grant `write` to no role a field worker holds. So the mobile
attach route was refusing nine of the eleven doctypes it advertises, for every
caller it was built for. The asset photograph is simply the one somebody hit
often enough to report.

The three gates in front of it were *narrower* than the DocPerm standing behind
it — one of them is a company scope Frappe cannot express without a User
Permission per row. The stricter check ran first and the looser one overruled it.

---

## The fix

`tools/files.py` grows one function:

```python
attach_file_to_authorized_parent(args)   # skips ONE check
```

It is the write-side twin of `list_attachments_on_authorized_parent` (v0.100.1),
and it makes the same argument that one makes: a caller whose right to the parent
was proved by a stricter route does not need to prove it again to a weaker one.

**What it skips is `frappe.has_permission(parent, "write")` and nothing else.**
The parent still must exist. It still may not be cancelled. It still must match
the company if one is named. The extension still goes through the site's own
allowlist, the duplicate check still runs, `max_attachments` is still honoured.
Those are facts about the *document*; the permission is a fact about the
*session*, and only the session fact had already been established elsewhere.

`api/mobile.attach_file_to_document` now calls it. Nothing else does.

### The exemption cannot be reached by a caller

The choice is a keyword-only Python parameter on a private `_attach`, never a key
read off `args`. A tool schema advertises `additionalProperties: false` and no
layer in this app enforces it, so a flag read from the payload would be a way for
any MCP caller to spend this exemption on a Journal Entry. `registry.TOOLS` does
not list the function, and a test asserts that it never will.

### The MCP transport is unchanged

`attach_file_to_document` in `tools/files.py` still asks Frappe for `write`, still
returns the same refusal naming `docs/security.md`, and `newhire._paperwork` still
goes through it. The console keeps the permission model; the handset keeps the one
it already passed.

## Why the test suite was green the whole time

`tests_standalone` has asserted since v0.78.0 that a photograph can be filed
against the asset it registered. That test passed on every commit while the bench
refused every attempt, because the harness's `frappe.has_permission` double is
**default-allow** — it never consults roles and answers yes to anything a test did
not explicitly deny. The test was real; the question it asked was not the one the
bench asks.

`STORE.denied_permissions` is the only lever that makes the double say no, so
this release adds five tests built on it:

- **the regression** — deny `("Asset Register", "write")`, register, attach; the
  photograph is filed. This test **fails** against the code as it shipped in
  v0.151.0, which is what makes it worth having.
- **the control on the control** — the same denial, asked through `tools/files.py`
  instead of the wrapper, still refuses with "not permitted to write". Without
  this, a `denied_permissions` entry that quietly stopped biting would turn the
  regression test green against unfixed code and nobody would know.
- **standing down the write check stands down nothing else** — the same filename
  twice is still refused on the brokered path.
- **the company scope survives** — an attach against another entity's asset is
  still refused, with the DocPerm denied, because that scope is the check that
  replaced the one removed.
- **the door is not a registered tool.**

No doctype changed, no patch is needed, and no DocPerm was edited — a Custom
DocPerm on `Asset Register` would have been the other way to fix this, and it
makes Frappe ignore every standard permission that doctype has, for every role,
silently, at `bench migrate`.
