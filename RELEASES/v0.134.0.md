# v0.134.0 — the sweep, and the site that was innocent of the crime it was charged with

v0.132.0 fixed two instances of `coerce(...) or DEFAULT` and named the rest as
residue. This finishes the sweep — 22 call sites — and adds the thing that release
said was worth more than any single fix: **an AST scan with a reason-carrying
allowlist**, so the next one is caught by CI rather than by a person remembering.

The most useful part of this note is not the count. It is that the site everybody
agreed was the worst one turned out not to be broken the way everybody thought,
and the only reason that surfaced is that the test written to prove the fix
**failed**.

## The idiom, and the two shapes it comes in

    value = as_int(args, "key", DEFAULT) or DEFAULT

`as_int` already answers `DEFAULT` for a missing or empty value, so the trailing
`or` cannot fire on `None` and cannot fire on `""`. The only thing it can ever
catch is an explicit zero — which it replaces with the default, silently, and
reports success for.

The fix depends on the helper, and using the wrong one is a **silent no-op**:

| shape | helper | fix |
|---|---|---|
| A | `as_int(args, key, default)` — carries a default | delete the trailing `or` |
| B | `as_float(value, key)` — **no default**, answers `0.0` for absent, `""` and `0` alike | branch on the RAW value before coercing |

`as_float(args, key, None)` is not a valid call. Applying shape A to a shape-B
site looks exactly like a fix and does nothing. Both shapes are now encoded in the
scanner so nobody has to work it out from the helper's signature again.

## The site that was innocent

`tools/sales.py` carried the flagged idiom and was reported as the worst instance
in the set: an invoice line explicitly comped to `amount: 0`, repriced back to
`qty × rate`. The expression really was the idiom, and it really did invent a
figure for a stated zero.

**Removing it did not stop the reprice.** The test written to prove the fix failed
at `620.0 != 0.0`.

`SalesInvoiceDocument.validate` recomputes `amount` from `qty × rate` on **every**
validate — real ERPNext does this, and the harness models it deliberately, with a
docstring explaining that `tools/sales.py` is built around the fact. Whatever
`_manual_lines` writes into `amount` is overwritten before anybody can read it.

The control that settled it:

> a stated `amount: 615.50` was discarded **exactly** like a stated `0`.

A value that is not a zero cannot be the victim of a zero-dropping idiom. The
`or` was never the mechanism. Without that second assertion this release would
have shipped a green test over an unfixed bug, and the changelog would have
claimed a fix that did not exist.

**The real fix is the one the settlement path has always used**: derive
`rate = amount / qty` so the product survives validate.
`_settlement_lines_to_invoice_lines` has done this for a packer's stated gross
since the module was written; the manual path never did, which is why a stated
`amount` was silently ignored there in every case, not only at zero.
`create_sales_invoice` now does the same and **reports the adjustment** in a new
`rate_adjustments` key rather than moving a rate quietly. A negative `amount` is
refused, since deriving the rate from it would otherwise smuggle past the
`rate < 0` check that only ever saw a directly-stated rate.

## The bug hiding under six of the fixes

Six `limit` sites read `as_int(args, "limit", D) or D`. Deleting the `or` — the
obvious fix, and the one the shape rule prescribes — would have been **strictly
worse than the bug**.

Frappe reads `limit_page_length=0` as **NO LIMIT**. Confirmed in `harness.py`:

    cap = limit or limit_page_length
    if cap:
        rows = rows[: int(cap)]

So `limit: 0` would have become an unbounded table scan, and every existing test
would have stayed green. Those six now route through the existing `as_limit`
helper, whose docstring has stated the correct policy all along: *"An explicit 0
clamps to 1 rather than falling back to the default."* Two of them were
hand-rolled reimplementations of `as_limit` sitting beside it.

## What was fixed, by class

**A guard below that the `or` made unreachable** — the same shape as v0.132.0's QR
bug. `mutate.py` (`exchange_rate: 0` became `1.0` one line above `if rate <= 0:
raise`), `assets.py` (`depreciation_frequency_months`), `kpi.py` (`window_months`).

**Limits, via `as_limit` or an explicit `max(1, min(cap, ...))`** — `expenses.py`
×2, `receipts.py`, `read.py`, `dispatch.py`, `taxforms.py`.

**Already clamped, where the `or` only ever ate the zero** — `shifts.py`,
`universal_scan.py`, `owner.py`, `funnel.py` ×2.

**A zero the caller may well mean** — `anchors.py` ×3 (`day_window: 0` is "same
day"), `itgc.py` ×3, `spray_rei.py`, `disclosure.py` (`threshold_pct: 0` is "every
segment, however small").

**Shape B, branching on the raw value** — `sales.py`, `mutate.py`,
`blocklifecycle.py` (`acres: 0` inherited the Field's acreage — a different
number, from a different source, reported as the caller's), `disclosure.py`
(a section numbered `0` was renumbered to `10` and could be reordered behind one
that stated `5`).

**Refused rather than substituted, because zero is not a legal value** —
`cropprotect.py` and `state_tax.py` (a year), `ml_model.py` (a zero-second HTTP
timeout is not a shorter fetch, it is one that cannot succeed).

## The scan

`tests_standalone/test_zero_drop.py`. Finds `BoolOp(Or)` whose left operand is a
coercion call — anchored on the `or`, **not** on "the same default", because
anchoring on sameness misses the value-corruption class entirely, where the
fallback is `round(qty * rate, 2)` or `active_minutes(doc)`.

97 such sites in the tree. 78 are the harmless identity (`x or 0` maps `None → 0`
and `0 → 0` — the same answer either way) and are ignored by rule. 19 are flagged,
and every one is allowlisted with a stated reason.

Whether `or None` counts as an identity is decided **per call site, not per
helper**: `_money(x) or None` answers `None` either way because the helper's own
default is already zero, but `as_int(args, "x", 5) or None` answers `5` for absent
and `None` for a zero, and there the `or` is the whole mechanism. There is no site
of the second kind today; the rule is hardened against the one that lands later.

Controls, because a scan that finds nothing is indistinguishable from a scan that
looks for nothing:

| control | proves |
|---|---|
| re-break `kpi.py` | the scan **flags** a real site, with an actionable message |
| "fix" an allowlisted `budget_engine` line | a **stale** allowlist entry is caught, not silently honoured |
| scan a made-up expression against an allowlisted file | the allowlist matches by **expression**, not by filename |

That third one is the failure an allowlist is most prone to and that no green run
would ever reveal: keyed too loosely, any new zero-dropping line in an allowlisted
file is excused for free.

## What is deliberately NOT fixed

Every entry carries its reason. The rule that decides:

> **An explicit zero is only a distinct value for an ARGUMENT.** A Frappe `Int`,
> `Float`, `Currency` or `Percent` column has no empty state — an unset one reads
> back as `0` — so for a stored field "explicitly zero" and "never set" are the
> same bytes, and no fix at the coercion can separate them.

`sales.py`'s settlement twin is the sharpest case, and it was settled **on the
fieldtype rather than on the shape**: `gross_amount` is a `Currency` with doctype
default `"0"` on `Settlement Line Item` (`istable: 1`), read via
`receipts._lines_out(doc)`. Column class, and unfixable — the mirror image of the
manual path fixed above, which reads a caller's `items[]` dict.

`budget_engine.py` ×4 and `dispatch.py` are v0.132.0's two reverts, kept.

### A reason can be wrong while its verdict is right

The `budget_engine` entries first carried v0.132.0's reason: *removing the `or`
raises `ZeroDivisionError`*. A peer re-ran it four ways and it does not. Removing
**either** alone is safe; only removing **both** raises. The first entry is in
`compute_budget_actuals`, a function containing no division at all.

The verdict holds — both stay allowlisted, on the column-class rule — but the
mechanism was wrong, and it had been copied forward once already. The entries now
say so.

Worth knowing before anything here is cited as settled: **no test in
`test_budget.py` sets `threshold_pct` to `0`**, so the suite could never have
adjudicated it either way. A green run was not evidence.

## Numbers

Both from a clean `git archive` extraction of the commit tree, not the shared
working tree — which at the time carried two other sessions' files:

    217631c (v0.133.0)              12,665 tests — OK
    217631c + this release          12,697 tests — OK, skipped=6   (+32, exactly the tests added)

`ruff check` clean across the tree.

The extraction earned its keep. Run against the working tree the suite was green;
run against the extracted tree it failed, because the allowlist carried an entry
for `remittance.py` — a file that exists on disk, is untracked, and is therefore in
no committed tree. The entry was permanently stale and only the extraction could
say so. The scan now filters to git-tracked modules, with a test asserting it still
reaches 200+ of them, because a filter is exactly the kind of thing that quietly
narrows to nothing and turns every "not flagged" result into a vacuous pass.

## Coordination

Four sessions were briefed on this same sweep. `tools/mobile.py` and `tools/i9.py`
belong to v0.132.0's author and are untouched here — their three remaining sites
are allowlisted as another session's in-flight work rather than silently excused.
`erpnext_mcp/remittance.py` is untracked and disclaimed by every session that has
looked at it; it is left alone and deliberately NOT allowlisted — it is in no
committed tree, so an entry for it would be permanently stale. That was caught by
running the suite on the extracted commit tree rather than on the shared working
tree, which is the only place the difference is visible. `investment_report.py` is a peer's,
landing separately — the scan does not flag it, and the issue there is a real zero
reported as `null`, which is output-shaping loss rather than value corruption.
