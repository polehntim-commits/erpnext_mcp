# v0.126.0 — the tax lot search had never matched a parcel

The Parcel form's "Import from County GIS" has been in the app since v0.33.0.
Read against the live Wasco County server rather than against its own docstring,
its tax lot search could not succeed — not for a mistyped lot, not for a lot in
the next county, but for any tax lot in Wasco County, ever.

This release fixes it, and adds the search an operator can actually run without
transcribing five fields in the right order: the assessor's account number.

## The bug, which was two bugs pointing at each other

`MapTaxlot` on Wasco's FeatureServer is stored **space-delimited and unpadded**:

    2N 11E 1 CC 4039
    1N 13E 7 200

v0.33.0 sent the **compact ORMAP spelling** off a deed:

    MapTaxlot='2N11E35BA-01600'

Those two strings are never equal, so the `where` clause matched nothing. And an
ArcGIS query that matches nothing is not an error — it is an HTTP 200 with an
empty feature list, which this app reads, correctly, as "the county has no such
parcel". The form said:

> Wasco County, Oregon has no parcel matching that tax lot number. Nothing was
> changed.

Every word of that sentence was wrong, and it read as the county's problem.

The other direction was shut at the same time. The old allowlist —
`^[A-Za-z0-9][A-Za-z0-9.\-]{0,39}$` — refused anything containing a space, so an
operator who gave up on the deed's spelling and typed the county's own was told
it was "not shaped like a tax lot number". There was no value that both passed
validation here and matched a row there.

**NEITHER HALF WAS VISIBLE FROM THE TEST SUITE**, because the fixture had the
same mistake in it. `COUNTY_ANSWER` in `test_gis_import.py` carried
`"MapTaxlot": "2N11E35BA-01600"`, so the tests asserted that the app sent the
spelling the app sent. Forty-eight of them passed against a feature that could
not work. The fixture now carries what the layer actually holds.

## The translation

`_tax_lot_parts` reads the grammar off the layer rather than off a deed, and the
grammar was verified against **all 15,516 rows** rather than guessed:

| part     | shape                    | examples          |
|----------|--------------------------|-------------------|
| township | one digit, then N or S   | `1N`, `2N`, `5S`  |
| range    | two digits, then E or W  | `11E`, `13E`      |
| section  | one or two digits        | `7`, `35`, `0`    |
| quarter  | one or two letters, often absent | `CC`, `BA`, `A` |
| lot      | three to five digits     | `200`, `4039`     |

Nothing is zero-padded and nothing is hyphenated. Roughly a third of the county's
lots have no quarter at all.

Anything an operator is likely to type now resolves to the one spelling the
server will match:

| typed                  | sent                        |
|------------------------|-----------------------------|
| `2N 11E 1 CC 4039`     | `2N 11E 1 CC 4039`          |
| `2n11e35ba-01600`      | `2N 11E 35 BA 1600`         |
| `2N11E35BA01600`       | `2N 11E 35 BA 1600`         |
| `1N-13E-07-0200`       | `1N 13E 7 200`              |
| `1N.13E.7.200`         | `1N 13E 7 200`              |

**STILL AN ALLOWLIST AND NOT AN ESCAPE, and a tighter one than before.** The
value is formatted into a `where` clause evaluated by somebody else's server, in
a dialect this app does not implement and cannot test against. Every part is now
matched against digits and a known letter before it is formatted, so the clause
cannot contain a character no branch allowed — where v0.33.0 permitted any forty
characters of letters, digits, dots and hyphens.

**THE UNPADDED RUN-TOGETHER FORM IS REFUSED RATHER THAN GUESSED.** `2N11E7200`
could be section 7 lot 200 or section 72 lot 00, and both are real parcels
somewhere in the county. The compact spelling parses only because a deed pads the
section to two digits and the lot to five; an unpadded one gets a refusal that
says so and shows the shape that works.

## Searching by account number

`AccountNum=7503`.

A tax lot is five fields in a fixed order and a character wrong in any one of
them returns a real parcel somewhere else, with an owner's name and an acreage on
it that both look plausible. The account number is four digits off the top of a
tax statement and the layer's own integer key. It is the search that cannot be
mistyped into a different farm, and it is the number a person already has in
their hand when they are looking at a bill and wondering which block it is for.

`AccountNum` is `esriFieldTypeInteger`, so **the clause carries no quotes at
all** — quoting an integer column is the kind of thing an ArcGIS backend answers
with a type error rather than a match. `_account_clause` parses to an `int` and
formats from the `int`, which is a stronger guarantee than any allowlist: there
is no path from the caller's string to the string that is sent.

Zero is refused by name rather than read as empty. `str(x or "")` would turn a 0
into an empty string and report it as "which account?", which is a different and
wronger sentence than "they start at 1".

## On the form

The import dialog now has two boxes, Tax Lot Number and Account Number, and
**typing in one empties the other**. `tax_lot` is pre-filled from this form's
Assessor Parcel ID, which is the right default and would otherwise have made
"fill in one or the other" an error message on every single account-number
search. The rule is visible as you type instead of arriving after you press
Search; the refusal stays as the guard for anything that fills both anyway.

**THE ACCOUNT NUMBER IS PRINTED IN THE PREVIEW.** It has been extracted from the
county's answer since v0.33.0 — `COUNTIES["wasco"]["properties"]` has always
listed `account: ("AccountNum", "ACCOUNTNUM", "Account")` — parsed, carried
across the wire, and then dropped on the floor. It now appears on the result
line next to the tax lot, the taxpayer and both acreages, and again in the import
summary, because **no field on Parcel holds it** and it is what somebody types
into Account Number to pull the same parcel back next season.

Three ways to ask, and exactly one per call. Asking two together would hide which
one matched, and knowing what you asked is the whole value of the preview. The
"nothing found" sentence now names which of the three came back empty, since
"no parcel matching that account number" and "no parcel matching that point"
send somebody to look in two different places.

## The tests

`test_gis_import.py` goes from 48 to 73.

`TheTaxLotIsValidated` is now `TheTaxLotIsTranslatedAndValidated` and asserts the
county's spelling rather than the app's. `TheAccountNumberIsAnInteger` is new.
The new argument is asserted against **both** gates — Guest, and a user denied
write on Parcel — rather than assumed still gated because the old one is: a new
way to ask that skipped either would be a way for a Family Member to drive the
farm's server at the county.

**`TheWidgetAndTheMethodAgree` reads the JavaScript.** `query_county_parcels` is
a whitelisted method and Frappe forwards the form dict to whatever names it
declares, so an argument the browser sends that the method does not name is a
TypeError in a console nobody is watching, and an argument the method grew that
the browser never sends is a feature that shipped and does nothing. Neither is
visible from either file alone, and neither was visible to any test that read
only Python — which is exactly how an account box could have been added to the
dialog and wired to nothing. It pulls the keys out of the object literals
actually passed to `query_county` and compares them against the real signature,
rather than asserting a substring of a file where a mention in a comment would
pass.

Every claim here was checked against the live server as well as the double: 240
rows sampled across the layer round-trip through `canonical_tax_lot` unchanged,
and six of them were re-queried by both their compact spelling and their account
number, one hit each.
