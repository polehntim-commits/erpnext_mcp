**Deploy: v0.324.0 — On Hold for Farm Tasks (with FarmOps 0.66.0 (62))**

**Migrate**:
- Farm Task gains the state `On Hold` and the hold fields;
- Farm Task Assignment gains the state `Held`;
- two MCP switches;
- the patch `dispatch_board_on_hold_column`.

Tools: **1,150 → 1,152** (two writes, off by default).

**Why**

Tim's Tell-the-Farm note AFB-2026-00034: "We have not started removing trees yet."
- The Bing removal parent FT-2026-10-00002 had been Claimed since Oct 3 and showed as active work.
- Its notes said ON HOLD until the Mill Creek land transfer closes, so the hold lived only in free text.
- (It was released back to Available on 2026-10-12 with `reject_farm_task`.)

**What changed**
- **A held task records** `hold_reason` (required), `hold_until_event` ("Mill Creek land transfer closes",
  "Constancy go-live"), an optional `hold_until_date`, who held it and when, and the state it came from.
  It is not `Paused`, which is a worker stopping the clock mid-job.
- **Holding:**
  - ends any live claim as `Held`, not Rejected (minutes kept; evidence and history untouched);
  - takes a crew off the job;
  - takes the task out of the pool and off the worker's list.
  - `cascade=true` holds its step tasks (those whose parent is this task) too.
- **While held, the task cannot be claimed, assigned or started.** The refusal reads "… is on hold: <reason> —
  until <event / date>." Offline claims replayed later get the same refusal.
- **Release:**
  - a held Draft goes back to Draft; anything else goes to the pool;
  - `cascade` releases the held steps too;
  - optional auto-release: a daily job at 00:15 releases tasks whose `hold_until_date` has come (when
    `auto_release` is ticked), pushes a notice to whoever held it and to the task's creator, and comments on the
    task.
- **Every hold and release is a comment on the task's timeline**; through MCP it is also an Action Log row.
- **MCP:**
  - `hold_farm_task` and `release_farm_task` (both default OFF), also reachable as `document action=hold|release
    type=farm_task`;
  - `list_dispatch_board` gets an On Hold column, plus `on_hold=true|false`;
  - `create_farm_task` and `create_task_from_template` take `on_hold={reason, until_event, until_date,
    auto_release}`, so a task can be created held.
- **Desk:**
  - the Farm Task Dispatch Kanban gets an "On Hold" column; the patch appends it to an existing board without
    moving anything else;
  - the task form shows the hold section while the task is held.
- **Phone:**
  - `/mobile/list_held_tasks` is the greyed "On hold" section with the reason; anyone who sees the farm's work can
    read it;
  - `/mobile/hold_task` and `/mobile/release_task` are for Foreman and Farm Manager, queued offline, and harmless to
    replay.

**After deploy (the user applies the holds; nothing is written to OML by this release)**

1. Tick ERPNext MCP Settings → Hold Farm Task and Release Farm Task (or hold from the Desk / phone).
2. The Bing removal and its steps, as one call:
   `hold_farm_task task=FT-2026-10-00002 hold_reason="Waiting on the Mill Creek land transfer" hold_until_event="Mill Creek land transfer closes" cascade=true`.
   Check that FT-2026-10-00003 … -00006 are its steps (`parent_task`); hold any that are not individually.
3. The burn placeholders and the Constancy go-live items: `hold_farm_task … hold_until_event="Constancy go-live"`.
4. `list_dispatch_board on_hold=true` lists them. On the phone (0.66.0), Work and Today show them greyed in "On hold".
5. `run_post_deploy_check expected_version=0.324.0`, then `bench --site frontend clear-cache`.

**Build / server / phone**

Push and build with `ERPNEXT_MCP_VERSION=0.324.0`, then `bench --site frontend migrate` and restart. Ship FarmOps
**0.66.0 (62)** to TestFlight after the server. Older phones simply don't list held tasks, and the server still
refuses to let anyone claim them.
