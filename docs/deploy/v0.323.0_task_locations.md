**Deploy: v0.323.0 — a Farm Task covers one or more blocks, and pins can be dragged into place (with FarmOps 0.65.0 (61))**

**Migrate**:
- new child doctype Farm Task Location;
- Farm Task gains `locations`, `location_count` and `has_work_spot`;
- Field Pin gains the kind "Work Spot" and `moved_at`;
- Asset Register and Housing Unit gain `position_set_by`, `position_set_at` and `position_source`. Tools: **1,150 → 1,150**. Needs v0.322.0 first.

**Why**

Tim's Bing removal tasks (FT-2026-10-00002 to -00007 and -00010) cover two blocks, MC-CP ("Bing Block - MC") and MC-WM
("Wind Mecine - MC"). A task held one location, so they were filed against the parcel "Mill Creek - OML", and the
phone pinned them at the parcel's centre rather than over the work. Correcting that over MCP needed the location
fields on the Updatable Fields whitelist, which Tim does not want changed.

**What changed**
- **A task covers one or more places:** blocks (Field), tags (Asset Register) or Parcels, in the child list
  `locations`.
  - The first place is mirrored into the task's own Location, so every older reader keeps working.
  - A scan of any of the blocks finds the task, and so does `list_tasks_by_location`.
- **An optional explicit pin, the "Work Spot",** reuses the field-pin pattern: a Field Pin sourced on the task.
- **On the phone, a multi-block task is pinned at the combined, area-weighted centre** of its blocks, or at the work
  spot.
  - The task detail on FarmOps 0.65.0 names every block, draws their outlines and frames the whole job.
  - A one-place task's payload is unchanged.
- **The validated MCP way to set them** (not the whitelist):
  ```
  record action=update type=farm_task name=<task> body={"locations": [...], "work_spot": {...}}
  ```
  - `locations` takes block names, tickers or aliases ("MC-CP", "MC-WM", or the "Bing Block" group), or
    {location_type, location}. `work_spot` is {latitude, longitude}; `clear_work_spot` removes it.
  - **Checks:** every place exists, is on the task's company, and is not a retired tag. A Completed, Cancelled or
    Rejected task is refused. Everything is checked before anything is written.
  - **Switches:** it needs `allow_record` and `allow_create_farm_task`.
- **Creating tasks:** `create_farm_task` and `create_task_from_template` take the same `locations` / `work_spot`.
  Multi-block template tasks and contractor-job tasks can be raised over all their blocks at once.

**Moving a pin by hand** (Tim: "We used to have a way of moving a pin in the Desk")

- **Asset Register** kept its draggable pin (v0.154.0), but since v0.214.0 a fixed asset (a valve, a building, a
  cabin's tag) refused the form save a drag needed. **A drag now goes through Move asset:**
  - it asks "Why is it moving?" once the asset has a position;
  - it records who moved it, why, and where it was;
  - the form reloads with the new position. Cancelling puts the pin back.
- **Housing Unit and Field Pin** get the same draggable pin over the aerial, with the parcel and its blocks (or the
  pin's block) drawn underneath. Dragging fills the latitude and longitude, and saving writes them. A cabin's
  Asset Register tag moves with it; moving the tag (Move asset) moves the cabin.
- **Farm Task:** the map draws the union of the task's block outlines with the pin at their centre.
  - Dragging the pin sets the task's **Work Spot** right away, and the Work Spot overrides the centre.
  - "Map → Clear work spot" puts it back.
- **Who moved it and when** is stamped on every path (Desk save, Move asset, phone, MCP): `position_set_by`,
  `position_set_at` and `position_source` on Asset Register and Housing Unit, and `moved_by` / `moved_at` on
  Field Pin. Each map shows the line "Last set by … on … (Desk/Phone/MCP)".
- **Who may:** System Manager, Farm Manager and Foreman. The phone route adds the caller's entity scope.
- **On the phone (FarmOps 0.65.0),** a manager long-presses the task or asset map to drop the pin where the work is.
  - Asset moves use the existing `move_asset`, with a reason, queued offline.
  - Task pins use the new `/mobile/move_task_pin`, also queued offline. The same point twice is the same answer.

**After deploy: the Bing tasks (the user applies this, not this release)**

For each of FT-2026-10-00002 … -00007 and FT-2026-10-00010:

```
record action=update type=farm_task name=FT-2026-10-0000N body={"locations": ["MC-CP", "MC-WM"]}
```

The answer's `before` shows the parcel it replaced. The phone, refreshed, pins each task between the two blocks, and
the task detail on 0.65.0 outlines both.

Then `run_post_deploy_check expected_version=0.323.0`. After the migrate, also run `bench --site frontend clear-cache`
so the Desk serves the new map scripts; `erpnext_mcp.geo_map.asset_map_build` in the browser console should read
0.323.0.

**Build / server / phone**

Push and build with `ERPNEXT_MCP_VERSION=0.323.0`, then `bench --site frontend migrate` and restart. Ship FarmOps
**0.65.0 (61)** to TestFlight after the server. Older phones still get the corrected pin; they just draw no
outlines.

**Rollback**

Roll back to the v0.322.0 image. The child rows stay, and the primary Location still points at the first block.
